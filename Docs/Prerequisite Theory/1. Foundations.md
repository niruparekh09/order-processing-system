
Every concept exists because the one before it created a new problem. Let's follow the chain.

## 🌐 Part 1: HTTP + REST - Why Does the Web Work This Way?

### 🤔 First, WHY does HTTP exist at all?

Imagine you're building Amazon in 1994. You have:

- A catalog server in Seattle
- A customer's browser in New York
- A TCP socket connecting them

You could just... send raw bytes. But then you'd have to answer:

- _How does the browser know where one response ends and another begins?_
- _How does the server know what resource the browser wants?_
- _How does the browser know if the request succeeded or failed?_
- _How do you handle caching, compression, authentication?_

**HTTP is the answer to all of these.** It's a contract - a shared language - that any client and server can speak. Without it, every system would invent its own protocol and nothing could talk to anything else.

### 📦 HTTP: The Envelope Metaphor

Think of every HTTP request as a postal envelope:

```
┌─────────────────────────────────────────────┐
│  ENVELOPE (HTTP Request)                    │
│                                             │
│  To:      GET /api/products/123             │  ← Request Line
│  Headers: Content-Type: application/json   │  ← Metadata
│           Authorization: Bearer xyz...     │
│           Cache-Control: no-cache          │
│                                             │
│  Body: { "filter": "electronics" }         │  ← Payload
└─────────────────────────────────────────────┘

Response Envelope:
┌─────────────────────────────────────────────┐
│  Status: 200 OK                             │  ← Did it work?
│  Headers: Content-Type: application/json   │
│           ETag: "abc123"                   │  ← For caching
│                                             │
│  Body: { "id": 123, "name": "Laptop" }     │
└─────────────────────────────────────────────┘
```

**The critical insight:** HTTP is **stateless by design.** The server reads the envelope, processes it, responds - and _immediately forgets you exist._ The next request starts from zero.

### 🧠 Why Stateless? (This will come back in microservices)

Statelessness is what makes HTTP **horizontally scalable.**

```
Without stateless HTTP (e.g., sticky sessions):
Request 1 → Server A (stores your session)
Request 2 → MUST go to Server A (session lives there)
Request 3 → MUST go to Server A
Server A dies → 💥 user loses session

With stateless HTTP:
Request 1 → Server A (no session stored)
Request 2 → Server B (doesn't matter)
Request 3 → Server C (load balancer picks any)
Server A dies → Load balancer routes to B or C → ✅ seamless
```

**Amazon has tens of thousands of servers.** Stateless HTTP is why they can add or remove servers without your shopping cart breaking - the cart is stored in a database or JWT, not on a specific server.

### 🎯 REST: Stateless HTTP With Conventions

REST (Representational State Transfer) isn't a protocol - it's an **architectural style** that gives HTTP meaningful conventions. Roy Fielding defined it in 2000.

The core REST insight: **The internet is a giant graph of resources. Each resource has a URL. HTTP verbs define what you do to resources.**

```
RESOURCE:  /orders/456

GET    /orders/456        → Fetch order 456
POST   /orders            → Create a new order
PUT    /orders/456        → Replace order 456 entirely
PATCH  /orders/456        → Update part of order 456
DELETE /orders/456        → Delete order 456
```

### 🚦 HTTP Status Codes: The Vocabulary of Failure

Status codes are how servers communicate **what happened** without the client parsing the body.

```
2xx = ✅ Success
  200 OK          - Standard success
  201 Created     - Resource was created (POST)
  204 No Content  - Success, nothing to return (DELETE)

3xx = ↩️ Redirect
  301 Moved Permanently  - URL has changed forever
  304 Not Modified       - Your cached version is still valid

4xx = 🤦 You messed up (client error)
  400 Bad Request     - Your request is malformed
  401 Unauthorized    - Who are you? (not authenticated)
  403 Forbidden       - I know who you are, but no (not authorized)
  404 Not Found       - Resource doesn't exist
  409 Conflict        - Your request conflicts with current state
  429 Too Many Req.   - Rate limited

5xx = 💥 We messed up (server error)
  500 Internal Server Error - Generic server crash
  502 Bad Gateway           - Upstream service failed
  503 Service Unavailable   - Overloaded or down
  504 Gateway Timeout       - Upstream took too long
```

**Interview trap:** "What's the difference between 401 and 403?"

- 401 = Not authenticated. You haven't proven who you are.
- 403 = Authenticated but not authorized. I know it's you, but you don't have permission.

### 🔄 Idempotency: The Concept That Makes Distributed Systems Safe

**Idempotency** = Calling an operation multiple times produces the same result as calling it once.

Why does this matter? In distributed systems, **networks fail.** You send a request, the network drops. Did the server get it? You don't know. So you retry. But if retrying causes a double-charge, that's catastrophic.

```
Idempotent:     GET, PUT, DELETE
Not Idempotent: POST (by default)

GET /balance → Returns $500
GET /balance → Returns $500   ← safe to retry
GET /balance → Returns $500

POST /transfer { amount: 100 } → Deducts $100, balance = $400
POST /transfer { amount: 100 } → Deducts $100, balance = $300 ← 💥 DOUBLE CHARGE
POST /transfer { amount: 100 } → Deducts $100, balance = $200

vs.

POST /transfer { idempotencyKey: "txn-xyz-789", amount: 100 }
→ Deducts $100, balance = $400, stores key
POST /transfer { idempotencyKey: "txn-xyz-789", amount: 100 }
→ Sees key already processed → returns same response → balance stays $400 ✅
```

**Real-world:** Stripe, PayPal, and every serious payment API require idempotency keys on payment endpoints. Uber uses them for ride creation. It's not optional when money is involved.

---

### 🧠 Mental Model: HTTP + REST

> **HTTP is a shared envelope format. REST is the convention for what to write on the envelope. Statelessness is the reason the post office can scale to handle billions of letters by adding more sorters. Idempotency is why retrying a lost letter doesn't accidentally send it twice.**

---

### 💬 Common HLD Interview Questions on HTTP/REST

1. _"How would you design a REST API for a ride-sharing app like Uber?"_
   - Think: resources (rides, drivers, locations), HTTP verbs, status codes, versioning (`/v1/rides`)

2. _"What happens when a client retries a failed payment request?"_
   - Answer: Idempotency keys prevent double charges.

3. _"Why is REST stateless and what are the trade-offs?"_
   - Stateless = horizontally scalable, but sessions need external storage (Redis, JWTs).

## 🏦 Part 2: Database Transactions - Why You Can't Just Write to the DB

### 💣 The Problem: What Happens Without Transactions?

Let's say you're building a banking system. User transfers $500 from Account A to Account B.

```java
// Naive implementation (NO TRANSACTIONS)
accountA.setBalance(accountA.getBalance() - 500);  // Step 1: Debit A
accountRepository.save(accountA);

// ← CRASH HERE (server dies, power failure, network blip)

accountB.setBalance(accountB.getBalance() + 500);  // Step 2: Credit B  ← NEVER EXECUTES
accountRepository.save(accountB);
```

**Result:** $500 vanished. Account A lost it. Account B never got it. The bank just created money from nothing - or destroyed it.

This is the fundamental problem transactions solve: **multi-step operations must be atomic.** Either everything happens or nothing does.

### 🎲 What Is a Transaction?

A transaction is a **unit of work** that groups multiple database operations so they succeed or fail **together.**

```java
// Spring Boot - proper implementation
@Transactional
public void transfer(Long fromId, Long toId, BigDecimal amount) {
    Account from = accountRepository.findById(fromId);
    Account to = accountRepository.findById(toId);

    from.setBalance(from.getBalance().subtract(amount));
    to.setBalance(to.getBalance().add(amount));

    accountRepository.save(from);
    accountRepository.save(to);

    // If ANYTHING throws an exception → ROLLBACK: both changes undone
    // If all succeeds → COMMIT: both changes persist permanently
}
```

The `@Transactional` annotation tells Spring: "Wrap this method in a database transaction. If it throws a RuntimeException, roll everything back."

## ⚗️ Part 3: ACID - The Four Laws of Transaction Physics

ACID is the set of guarantees that a reliable database must provide for transactions. These aren't optional features - they're the foundation.

### A - Atomicity ☢️

**"All or nothing."**

The transaction either commits completely or rolls back completely. There is no partial success.

```
Transfer $500 from A to B:

COMMIT path:
  Debit A ✓
  Credit B ✓
  → Both changes persist

ROLLBACK path:
  Debit A ✓
  Credit B ← FAILS (account B frozen, doesn't exist, etc.)
  → Debit A is UNDONE → balance restored

No middle ground. Ever.
```

**Analogy:** A flight booking. Either you get your seat on the plane AND your credit card is charged, OR neither happens. You never end up charged with no seat.

---

### C - Consistency 📏

**"The database must go from one valid state to another valid state."**

Consistency means your business rules (constraints, foreign keys, CHECK constraints) are never violated by a transaction.

```sql
-- Database constraint: balance CANNOT go below 0
ALTER TABLE accounts ADD CONSTRAINT balance_non_negative CHECK (balance >= 0);

-- Transaction tries to overdraft:
UPDATE accounts SET balance = -100 WHERE id = 1;

-- DB enforces constraint → REJECTS the transaction
-- The constraint violation rolls back the entire transaction
```

**Important nuance:** Consistency in ACID is slightly different from the C in CAP theorem (which is about distributed systems). ACID Consistency = business rule enforcement. CAP Consistency = all nodes see the same data at the same time.

---

### I - Isolation 🏝️

**"Concurrent transactions don't interfere with each other."**

This is the trickiest one. Isolation determines what one transaction can "see" from other in-progress transactions.

Imagine two users simultaneously reading and writing the same bank account:

```
Time    Transaction 1 (T1)         Transaction 2 (T2)
────    ──────────────────         ──────────────────
t=1     BEGIN
t=2     READ balance → $1000
t=3                                BEGIN
t=4                                READ balance → $1000
t=5     WRITE balance = $500
t=6                                WRITE balance = $800  ← based on stale $1000!
t=7     COMMIT
t=8                                COMMIT
```

**Result:** T1 deducted $500. T2 deducted $200 (from its perspective of $1000). But the final balance is $800 - **T1's write was silently overwritten.** This is called a **Lost Update**.

Isolation prevents this by controlling what transactions can see from each other.

#### Isolation Levels (from weakest to strongest):

```
┌─────────────────────┬────────────┬──────────────┬──────────────┐
│ Isolation Level     │ Dirty Read │ Non-Repeat.  │ Phantom Read │
│                     │            │ Read         │              │
├─────────────────────┼────────────┼──────────────┼──────────────┤
│ READ UNCOMMITTED    │ ✅ SAFE    │ ❌ POSSIBLE  │ ❌ POSSIBLE  │
│ READ COMMITTED      │ ✅ SAFE    │ ✅ SAFE      │ ❌ POSSIBLE  │
│ REPEATABLE READ     │ ✅ SAFE    │ ✅ SAFE      │ ❌ POSSIBLE  │
│ SERIALIZABLE        │ ✅ SAFE    │ ✅ SAFE      │ ✅ SAFE      │
└─────────────────────┴────────────┴──────────────┴──────────────┘
```

Let's decode the anomalies:

**Dirty Read:** You read data that another transaction wrote but hasn't committed yet. If that transaction rolls back, you read data that _never officially existed._

```
T1: UPDATE balance = -9999 (not committed yet)
T2: READ balance → sees -9999 ← DIRTY READ
T1: ROLLBACK (balance never was -9999)
T2: Made a decision based on a lie
```

**Non-Repeatable Read:** You read a row twice in the same transaction and get different values because another transaction modified it between your reads.

```
T1: READ order.status → "pending"
T2: UPDATE order.status = "shipped" → COMMIT
T1: READ order.status → "shipped"  ← different value, same transaction!
```

**Phantom Read:** You run the same query twice and get different _rows_ because another transaction inserted or deleted rows.

```
T1: SELECT count(*) FROM orders WHERE user_id=5 → 3 orders
T2: INSERT INTO orders (user_id=5, ...)  → COMMIT
T1: SELECT count(*) FROM orders WHERE user_id=5 → 4 orders ← phantom!
```

**Default in MySQL/InnoDB:** REPEATABLE READ
**Default in PostgreSQL:** READ COMMITTED
**Spring Boot default:** Inherits from the database

---

### D - Durability 💾

**"Once committed, data survives crashes."**

When the database says "COMMIT successful," that data is safe - even if the power goes out one millisecond later.

How? **Write-Ahead Logging (WAL):**

```
1. Transaction is committed
2. Before updating data files on disk,
   the change is written to a sequential WAL log file
3. WAL is durable (flushed to disk via fsync)
4. THEN the actual data pages are updated
5. If crash happens at step 4:
   → On restart, DB replays WAL log → data is recovered
```

**Analogy:** Before editing a document, you write your planned changes in a notebook. If your computer crashes mid-edit, you replay the notebook to recover.

---

### 🧠 Mental Model: ACID

> **Think of a database transaction as a bank vault operation:**
>
> - **Atomic:** Either the whole transfer happens or nothing does. No half-transfers.
> - **Consistent:** The vault's rules (no negative balances) are always enforced.
> - **Isolated:** Two tellers serve two customers simultaneously but their operations don't interfere - as if they happened one after another.
> - **Durable:** Once the transaction receipt is printed, the operation survives a power outage.

---

### ⚠️ Common Beginner Misconceptions About ACID

❌ **"@Transactional catches all exceptions and rolls back"**
✅ By default, Spring's `@Transactional` only rolls back on **unchecked exceptions** (RuntimeException and its subclasses). Checked exceptions (like `IOException`) do NOT trigger rollback by default.

```java
@Transactional(rollbackFor = Exception.class)  // ← Roll back on ALL exceptions
public void transfer() throws IOException { ... }
```

❌ **"Transactions prevent all concurrency issues"**
✅ They don't - isolation level determines WHICH concurrency issues are prevented. Using `READ COMMITTED` still allows phantom reads.

❌ **"Higher isolation = always better"**
✅ Higher isolation = fewer anomalies BUT more locking = lower throughput. `SERIALIZABLE` can make a high-traffic system grind to a halt. There are always trade-offs.

## ⚡ Part 4: Concurrency - When Many Things Happen At Once

### The Core Problem

Your single-threaded mental model:

```
User A requests balance
Database reads balance (500)
User A gets 500
```

Reality with 10,000 concurrent users:

```
Thread 1: reads balance (500) → plans to deduct 100
Thread 2: reads balance (500) → plans to deduct 200
Thread 1: writes balance (400) → commits
Thread 2: writes balance (300) → commits ← 💥 overwrites Thread 1's deduction!
Final balance: 300 instead of 200
```

This is the **Lost Update** problem. $100 effectively vanished.

### The Two Strategies: Pessimistic vs Optimistic Locking

The fundamental choice in concurrency control:

```
PESSIMISTIC: "I assume conflict WILL happen, so I lock first"
OPTIMISTIC:  "I assume conflict WON'T happen, so I just check at the end"
```

Choosing between them is one of the most important trade-off decisions in backend design.

---

### 🔐 Pessimistic Locking: Lock First, Ask Questions Later

**How it works:** When you read a row you intend to modify, you **lock it immediately.** No one else can touch it until you're done.

```sql
-- Pessimistic lock in SQL
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;  ← Locks this row
-- Other transactions trying to SELECT FOR UPDATE on id=1 → BLOCKED

UPDATE accounts SET balance = balance - 500 WHERE id = 1;
COMMIT;  ← Lock released
```

In Spring Data JPA:

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT a FROM Account a WHERE a.id = :id")
Account findByIdForUpdate(@Param("id") Long id);
```

**Analogy:** You put a "DO NOT DISTURB" sign on a hotel room when you enter. Nobody else can enter until you leave.

**When to use:**

- High contention: many users fighting over the same rows
- Short transactions
- When you really cannot afford any conflicts (bank transfers, inventory deduction)

**Risks:**

- **Deadlock:** Two transactions each hold a lock the other needs

```
T1 locks Row A, tries to lock Row B
T2 locks Row B, tries to lock Row A
→ Neither can proceed → deadlock → DB kills one transaction
```

- **Reduced throughput:** Locks mean waiting. High-traffic systems can queue up behind locks.
- **Lock timeout:** Transaction holds lock too long → others timeout → cascading failures

---

## 🔮 Part 5: Optimistic Locking - The Netflix Approach

### The Insight

In most systems, **conflicts are rare.** Multiple users rarely edit the _same record_ at the _exact same time._ So why pay the cost of locking for every read?

Optimistic locking says: **"Don't lock. Just detect conflicts when they happen."**

### How It Works: The Version Number

Every row gets a `version` column:

```sql
CREATE TABLE products (
    id BIGINT PRIMARY KEY,
    name VARCHAR(255),
    stock INT,
    version INT DEFAULT 0  ← the key
);
```

**Read phase:** Read the row + its version number. No lock taken.

**Write phase:** When updating, check that the version hasn't changed since you read it.

```sql
UPDATE products
SET stock = :newStock,
    version = version + 1        ← increment version
WHERE id = :id
  AND version = :expectedVersion; ← check version hasn't changed
```

If `version` changed (someone else modified it), the `WHERE` clause matches zero rows. You detect the conflict and retry.

### Spring Boot Implementation

```java
@Entity
public class Product {
    @Id
    private Long id;

    private int stock;

    @Version  ← Spring/Hibernate handles everything
    private int version;
}
```

With `@Version`, Hibernate automatically:

1. Adds `AND version = ?` to all UPDATE statements
2. Increments the version on every save
3. Throws `OptimisticLockException` if version mismatch → you catch this and retry

### 🎬 Real-World Example: Netflix Watch History

Imagine Netflix updating your watch history:

```
You start watching Stranger Things at 8pm (version=5)
Two browser tabs are open (laptop + phone)

Phone pauses at 23:45 (version=5)
Laptop pauses at 25:12 (version=5)

Phone saves: UPDATE history SET position=23:45, version=6 WHERE version=5 → SUCCESS
Laptop saves: UPDATE history SET position=25:12, version=7 WHERE version=6 ← expects 5, got 6 → CONFLICT!

Laptop detects conflict → re-reads current state (version=6, position=23:45)
→ Merges or takes latest → saves (version=7, position=25:12) → SUCCESS
```

Netflix can handle millions of these without any row-level locking degrading performance.

### ⚔️ Pessimistic vs Optimistic: The Decision Matrix

```
┌────────────────────┬──────────────────────┬──────────────────────┐
│                    │ PESSIMISTIC          │ OPTIMISTIC           │
├────────────────────┼──────────────────────┼──────────────────────┤
│ Conflict rate      │ High                 │ Low                  │
│ Throughput         │ Lower (waiting)      │ Higher (no waiting)  │
│ Deadlock risk      │ YES                  │ No                   │
│ Stale reads        │ No                   │ Possible             │
│ Retry logic needed │ No                   │ YES                  │
│ Use case           │ Bank debits,         │ User profiles,       │
│                    │ inventory (-1 item)  │ content metadata,    │
│                    │                      │ watch history        │
└────────────────────┴──────────────────────┴──────────────────────┘
```

**The key question to ask in an interview:** _"How often do two users modify the same record simultaneously?"_

- Often → Pessimistic
- Rarely → Optimistic

---

### 🧠 Mental Model: Optimistic Locking

> **Optimistic locking is like editing a shared Google Doc offline.** You download the doc, make edits, then try to sync. If someone else changed it while you were offline, Google Docs detects the conflict and asks you to resolve it. No one was "locked out" while you were editing - you just need to handle conflicts if they occur.

---

### 💬 HLD Interview Questions on Transactions/Locking

1. _"How would you handle concurrent seat booking for a concert (10,000 users fighting for 100 seats)?"_
   - Pessimistic locking on individual seats. Or: reserve seats with a short lease TTL, use a distributed lock (Redis SETNX).

2. _"You have a flash sale where 10,000 requests hit simultaneously for 500 items. How do you prevent overselling?"_
   - Pessimistic lock + `WHERE stock > 0` in the UPDATE, or an atomic SQL: `UPDATE inventory SET stock = stock - 1 WHERE stock > 0 AND product_id = ?` - let the DB enforce it.

3. _"What is a deadlock and how do you prevent it?"_
   - Two transactions waiting for each other's locks. Prevention: always acquire locks in the same order. Detection: DB detects and kills one.

## 🏙️ Part 6: Microservices Boundaries - When Monoliths Break

### The Monolith First

Before microservices, there was the monolith. Not as a failure - as a starting point.

```
MONOLITH (early Amazon, early Netflix, early Uber):

┌─────────────────────────────────────────────┐
│              Single Application             │
│                                             │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  │
│  │  Orders  │  │  Users   │  │Inventory │  │
│  └──────────┘  └──────────┘  └──────────┘  │
│         │            │            │         │
│         └────────────┴────────────┘         │
│                      │                      │
│              Single Database                │
└─────────────────────────────────────────────┘
```

**Monolith advantages (don't dismiss these):**

- Simple to develop and debug
- No network calls between components (just method calls)
- ACID transactions across all data
- Easy to test end-to-end
- Single deployment

**What breaks at scale:**

```
At startup: 5 engineers, 1 service, 1000 requests/day → Monolith is perfect

At scale:  500 engineers, "the whole team needs to agree before deploying"
           → 10 teams blocked by 1 team's bug
           → Payment service is CPU-heavy, User service is memory-heavy
              → Can't scale them independently
           → One bad deploy takes down EVERYTHING
```

Netflix's story: In 2008, a database corruption took Netflix offline for 3 days. A single failure point. They spent the next 7 years migrating to microservices.

---

### 📦 What Is a Microservice?

A microservice is a **small, independently deployable service that owns one business capability and its own data.**

Key parts of that definition:

1. **Small** - one team, one responsibility
2. **Independently deployable** - you can deploy the Orders service without touching the Users service
3. **Owns one business capability** - not a technical slice (not "the database layer"), but a business domain
4. **Owns its own data** - this is the hard part

```
MICROSERVICES (modern Uber):

┌─────────────┐   ┌─────────────┐   ┌─────────────┐
│   Rides     │   │   Users     │   │  Payments   │
│   Service   │   │   Service   │   │   Service   │
│             │   │             │   │             │
│  Rides DB   │   │  Users DB   │   │ Payments DB │
└─────────────┘   └─────────────┘   └─────────────┘
       │                │                  │
       └────────────────┴──────────────────┘
                        │
               Message Bus / API Gateway
```

Each service has its **own database.** This is non-negotiable and also the source of all the hard problems.

---

### 🗺️ How to Draw Microservice Boundaries (Domain-Driven Design)

The hardest question: **Where do you cut?**

Bad boundary: Cut by technical layer ("the frontend service," "the database service")
Good boundary: Cut by **business domain** (bounded context in DDD)

**Heuristic:** If two things change together, they belong together. If they change independently, they're separate services.

```
"When an order is placed, we update order status, send email, deduct inventory,
charge payment, and notify the driver"

→ These can evolve independently:
  - Order Service: manages order lifecycle
  - Notification Service: handles emails/SMS
  - Inventory Service: stock management
  - Payment Service: billing and refunds
  - Driver Service: assignment and tracking

→ But: Order status and order items always change together
  → Keep them in Order Service, not separate
```

**Real systems:**

```
Netflix:
- Catalog Service    (what shows exist)
- Streaming Service  (video delivery)
- Recommendations    (what to watch next)
- User Profile       (preferences, history)
- Billing            (subscriptions, payments)

Uber:
- Rider Service      (user-facing requests)
- Driver Service     (driver app, location)
- Matching Service   (connect rider + driver)
- Pricing Service    (surge, estimates)
- Trip Service       (active ride management)
- Payment Service    (charging, tipping)
```

---

### 💥 The Problem Microservices Create: No ACID Across Services

Here's the devastating consequence of microservice boundaries:

```
Monolith - place an order:
@Transactional
public void placeOrder(Order order) {
    orderRepo.save(order);          // ← same DB
    inventoryRepo.deduct(item, 1);  // ← same DB
    paymentRepo.charge(card, price);// ← same DB
    // All in ONE transaction → ACID guaranteed
}

Microservices - place an order:
public void placeOrder(Order order) {
    orderService.createOrder(order);      // HTTP call to Order Service
    inventoryService.deduct(item, 1);     // HTTP call to Inventory Service
    paymentService.charge(card, price);   // HTTP call to Payment Service

    // What if paymentService.charge() fails after the first two succeed?
    // → Order exists, inventory deducted, but payment failed
    // → NO AUTOMATIC ROLLBACK across services
    // → 💥 DATA INCONSISTENCY
}
```

This is the **fundamental tension of microservices:** you gain independent scalability and deployability, but you lose ACID.

---

### 🔧 Solutions to Cross-Service Consistency

#### 1. The Saga Pattern

A Saga is a sequence of local transactions, each publishing an event that triggers the next step. If any step fails, compensating transactions undo previous steps.

```
CHOREOGRAPHY-BASED SAGA (event-driven):

Order Service:     placeOrder() → emits "OrderPlaced" event
                                          ↓
Inventory Service: listens to "OrderPlaced" → reserves stock → emits "StockReserved"
                                                                        ↓
Payment Service:   listens to "StockReserved" → charges card → emits "PaymentSucceeded"
                                                                        ↓
Order Service:     listens to "PaymentSucceeded" → confirms order → "OrderConfirmed"

If payment FAILS:
Payment Service: emits "PaymentFailed"
                         ↓
Inventory Service: listens to "PaymentFailed" → RELEASES reserved stock (compensating tx)
                         ↓
Order Service: listens → CANCELS order (compensating tx)
```

**Analogy:** Booking a trip through a travel agent. Agent books flight, hotel, car. If the hotel is unavailable, they automatically cancel the flight and car - each step is reversible with a compensating action.

#### 2. Outbox Pattern (Transactional Outbox)

Problem: How do you reliably publish an event after a DB write? What if the service crashes between the write and the publish?

```
WRONG:
1. Save order to DB          ← commits
2. Publish "OrderPlaced" to Kafka  ← CRASHES HERE → event never sent!

OUTBOX PATTERN:
1. BEGIN TRANSACTION
   Save order to orders table
   Save "OrderPlaced" event to outbox table  ← same transaction!
2. COMMIT (both happen atomically)
3. Separate "outbox processor" reads outbox table and publishes to Kafka
   → At-least-once delivery → idempotent consumers handle duplicates
```

This is how Amazon, Uber, and most serious distributed systems guarantee "at least once" event delivery.

### 📡 Inter-Service Communication: Sync vs Async

```
SYNCHRONOUS (HTTP/gRPC):
User → Order Service → HTTP → Inventory Service
                            ↑
                       If Inventory is down → Order fails immediately

Pros: Simple, immediate response
Cons: Coupling, cascading failures

ASYNCHRONOUS (Message Queue: Kafka, RabbitMQ, SQS):
User → Order Service → Kafka → Inventory Service (processes when ready)
                            ↑
                       If Inventory is down → message waits in queue

Pros: Decoupled, resilient, buffer
Cons: Eventual consistency, harder to debug, need idempotent consumers
```

**Rule of thumb:**

- User-facing, needs immediate response → Synchronous
- Background work, can be delayed → Asynchronous
- Critical business events (order placed, payment processed) → Async + persistent queue

### 🔌 The API Gateway Pattern

With 20 microservices, you can't expose all of them to clients. Enter the API Gateway:

```
Client
  │
  ▼
┌─────────────────────────────────────┐
│            API GATEWAY              │
│  (Authentication, Rate Limiting,    │
│   Routing, SSL Termination,         │
│   Request Aggregation)              │
└─────────────────────────────────────┘
  │           │           │
  ▼           ▼           ▼
Orders     Users       Payments
Service    Service     Service
```

**What the gateway does:**

- Single entry point → clients don't need to know about service topology
- Authenticates JWT once, forwards identity downstream
- Rate limits to prevent abuse
- Can aggregate responses (one client request → calls 3 services → merged response)

**Real examples:** Netflix Zuul, Kong, AWS API Gateway, Spring Cloud Gateway

### 🧠 Mental Model: Microservices

> **Think of microservices like different departments in a large company.** HR, Engineering, Finance, and Sales each have their own filing cabinets (databases), their own budgets, and can be reorganized independently. They communicate via email (events/APIs). The trade-off is that a company-wide transaction (fire someone → remove from payroll → remove from systems → send severance) requires coordination across departments - there's no single authority that atomically does all of this. You need a process (saga) with compensating steps if something fails.

### ⚠️ Common Beginner Misconceptions About Microservices

❌ **"Microservices are always better than monoliths"**
✅ Monoliths are often the right choice - especially early-stage. Start with a modular monolith, extract services when you have a clear reason (scale, team autonomy, deployment independence).

❌ **"Each REST endpoint should be a service"**
✅ Services are bounded by business domains, not technical operations. A "User Service" handles registration, profile, authentication, preferences - all user-related concerns.

❌ **"Shared database is fine as long as services are separate"**
✅ Shared DB = shared schema = tight coupling. If Order Service and Payment Service share a DB, you can't evolve their schemas independently. The key to microservices freedom is database-per-service.

❌ **"Microservices solve consistency problems"**
✅ They create them! Microservices trade ACID transactions for scalability and autonomy. You must explicitly design for eventual consistency.

## 🔗 Part 7: How It All Connects - The Full Picture

Let's trace what happens when you order something on Amazon:

```
1. Browser sends HTTP POST /orders (REST)
   → Idempotency key in header to prevent double-orders

2. API Gateway authenticates JWT, routes to Order Service

3. Order Service begins processing:
   - Writes order to DB (ACID transaction)
   - Writes "OrderPlaced" event to outbox table (same transaction → Atomic)
   - COMMITS

4. Outbox processor publishes "OrderPlaced" to Kafka

5. Inventory Service (async):
   - Reads "OrderPlaced"
   - Starts local transaction (ACID)
   - Checks stock with optimistic locking (@Version)
   - Deducts stock
   - Commits → publishes "StockReserved"

6. Payment Service (async):
   - Reads "StockReserved"
   - Charges idempotently (idempotency key = order ID)
   - Commits → publishes "PaymentSucceeded"

7. Order Service:
   - Reads "PaymentSucceeded"
   - Updates order status to "Confirmed" (ACID transaction)

8. Notification Service:
   - Reads "PaymentSucceeded"
   - Sends email (idempotently - no duplicate emails)

IF ANY STEP FAILS:
   Compensating transactions roll back upstream services
   → Saga ensures eventual consistency
```

**Notice how every concept appeared:**

- HTTP/REST: client-server communication
- Idempotency: safe retries
- ACID: each service's local data integrity
- Isolation levels: stock deduction under concurrency
- Optimistic locking: concurrent inventory updates
- Microservices: independent scaling of order, payment, inventory
- Saga: cross-service consistency without distributed transactions
- Outbox: reliable event publishing

## 🧮 Quick Reference: Trade-off Cheat Sheet

```
┌──────────────────────┬──────────────────┬───────────────────────┐
│ CONCEPT              │ GAIN             │ COST                  │
├──────────────────────┼──────────────────┼───────────────────────┤
│ Stateless HTTP       │ Horizontal scale │ Session externalized  │
│ Higher isolation     │ Fewer anomalies  │ Lower throughput      │
│ Pessimistic locking  │ No conflicts     │ Deadlocks, queuing    │
│ Optimistic locking   │ High throughput  │ Retry logic needed    │
│ Microservices        │ Scale, autonomy  │ No distributed ACID   │
│ Sync communication   │ Immediate answer │ Coupling, cascades    │
│ Async (queues)       │ Resilience       │ Eventual consistency  │
│ SERIALIZABLE txns    │ Zero anomalies   │ Low concurrency       │
│ READ COMMITTED txns  │ High concurrency │ Non-repeatable reads  │
└──────────────────────┴──────────────────┴───────────────────────┘
```

## 🎯 Final Mental Models to Carry Into Every Interview

**On HTTP:** "The stateless envelope format that lets us scale horizontally by removing server-side session state."

**On Transactions:** "A unit of work that groups operations so they succeed or fail together. The ACID properties describe what 'reliable' means for that unit."

**On ACID:** "Atomicity=all or nothing. Consistency=rules always hold. Isolation=concurrent transactions don't interfere. Durability=commits survive crashes."

**On Concurrency:** "Multiple actors writing shared state concurrently will corrupt it without coordination. The choice is when to coordinate: before (pessimistic) or after (optimistic)."

**On Optimistic Locking:** "Assume no conflict, verify at write time using version numbers. If conflict detected, retry. High throughput at low-conflict rates."

**On Microservices:** "Trade ACID across the system for independent deployability and scalability. Each service owns its data. Cross-service consistency requires explicit patterns (sagas, outbox, idempotency)."

**The overarching theme:** Every one of these patterns exists because of a specific failure mode. HTTP solves protocol chaos. Transactions solve partial writes. ACID properties each solve a specific class of data corruption. Locking solves race conditions. Microservices solve monolith scaling. Sagas solve cross-service inconsistency. **Learn the failure first. The solution makes itself obvious.**
