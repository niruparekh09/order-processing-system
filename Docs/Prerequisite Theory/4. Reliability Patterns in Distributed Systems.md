# 🛡️ Reliability Patterns in Distributed Systems

_How production systems stay alive when everything around them is trying to die._

---

## 🗺️ The Map

```
FAILURE CLUSTER 1: The Dual Write Problem
  Database succeeded, Kafka failed → Transactional Outbox
  Outbox publishes duplicates → Idempotent consumers
  ↓
FAILURE CLUSTER 2: Downstream Service Failures
  Service unavailable → Retry
  Retry makes it worse → Exponential backoff + Jitter
  Service is never recovering → Circuit Breaker
  Circuit heals → Half-open recovery
  ↓
FAILURE CLUSTER 3: Speed Mismatch
  Producer faster than consumer → Consumer lag
  Lag grows unbounded → Backpressure
  Backpressure ignored → System collapse
  ↓
HOW THESE CONNECT IN REAL SYSTEMS
```

Every pattern is a scar. Something broke in production, engineers fixed it, and the fix became a pattern. Let's find the original wounds.

---

## 💀 Part 1: The Dual Write Problem - The Root of All Event Bugs

### The Innocent-Looking Code That Causes Disasters

Imagine your Order Service after a user places an order. You need to do two things: save the order to your database, and publish an "OrderPlaced" event to Kafka so downstream services (Inventory, Payment, Notification) can react.

The naive code looks like this:

```
Step 1: Save order to PostgreSQL → SUCCESS
Step 2: Publish OrderPlaced to Kafka → ?
```

Simple enough. But now let's ask the uncomfortable question: what can go wrong between Step 1 and Step 2?

---

### 🎯 Failure Scenario A: Database Succeeds, Kafka Fails

```
Timeline:

t=0  BEGIN transaction
t=1  INSERT order #5678 into orders table  ✅
t=2  COMMIT                                ✅
     (Order is now permanently in the DB)
t=3  Kafka broker is temporarily unavailable 💥
     Publisher gets a connection timeout
t=4  What now?

State of the world:
  PostgreSQL: order #5678 EXISTS
  Kafka:      OrderPlaced event NEVER PUBLISHED

  Inventory Service:  has no idea order was placed
  Payment Service:    has no idea order was placed
  Notification Service: has no idea order was placed

  User:  sees "Order confirmed!" (you showed them the DB result)
  Reality: order is stuck forever. Nobody will process it.
```

This is the **dual write problem**. You're writing to two separate systems (DB + Kafka) and there is no atomic transaction spanning both. One can succeed while the other fails.

Your options in the naive design are all bad:

| Option                            | What You Do                       | What Goes Wrong                                                        |
| --------------------------------- | --------------------------------- | ---------------------------------------------------------------------- |
| Publish first, then save          | Publish event, then save to DB    | Event published for order that fails to save → ghost event             |
| Save first, then publish          | Save to DB, then publish to Kafka | DB saves, Kafka fails → orphaned order, never processed                |
| Wrap in try-catch and retry       | Retry Kafka publish on failure    | If DB transaction rolled back between tries, you publish for nothing   |
| Use distributed transaction (2PC) | Atomic commit across DB and Kafka | Kafka doesn't support XA transactions. 2PC is fragile at scale anyway. |

None of these work reliably. The fundamental issue is that **two separate systems cannot be written to atomically without a shared transaction coordinator**, and no such coordinator exists between PostgreSQL and Kafka.

---

### 📬 The Transactional Outbox: Writing to One System Twice

The Transactional Outbox pattern solves the dual write problem with a beautiful insight:

> **Instead of writing to the database AND Kafka, write to the database TWICE. The second write goes into an "outbox" table. A separate process reads the outbox and publishes to Kafka.**

```
BEFORE (dual write - broken):

Order Service
    ├── writes to → PostgreSQL (orders table)
    └── writes to → Kafka (OrderPlaced event)
         ↑
    Two separate systems, no shared transaction

AFTER (Outbox pattern - reliable):

Order Service
    └── ONE transaction writes to:
         ├── PostgreSQL (orders table)
         └── PostgreSQL (outbox table)  ← same DB, same transaction!

Outbox Processor (separate process)
    └── reads outbox table
    └── publishes to Kafka
    └── marks outbox entry as published
```

Let's see what the data looks like:

```
orders table:
┌──────────┬──────────────┬──────────────┬──────────────┐
│ order_id │ user_id      │ amount       │ status       │
├──────────┼──────────────┼──────────────┼──────────────┤
│ 5678     │ u-123        │ 999.99       │ PENDING      │
└──────────┴──────────────┴──────────────┴──────────────┘

outbox table:
┌──────────┬────────────────┬────────────────────┬──────────────┬───────────────┐
│ id       │ event_type     │ payload            │ published    │ created_at    │
├──────────┼────────────────┼────────────────────┼──────────────┼───────────────┤
│ 1        │ OrderPlaced    │ {"orderId":"5678"} │ false        │ 09:47:03      │
└──────────┴────────────────┴────────────────────┴──────────────┴───────────────┘
```

Both rows are written in the same PostgreSQL transaction. If the transaction commits, both exist. If it rolls back, neither exists. The dual write problem is eliminated.

The outbox processor then runs independently:

```
Outbox Processor loop (runs every 100ms or triggered by DB change):

1. SELECT * FROM outbox WHERE published = false ORDER BY created_at
2. For each unpublished event:
   a. Publish to Kafka
   b. If publish succeeds: UPDATE outbox SET published = true WHERE id = ?
   c. If publish fails: leave it as published=false, retry next loop
```

---

### 🔍 Now Let's Replay the Same Failure Scenarios

**Scenario A: DB transaction fails**

```
BEGIN transaction
INSERT INTO orders ... → succeeds
INSERT INTO outbox ... → succeeds
COMMIT → FAILS (disk full, DB crash, etc.)

Result: Both rows are rolled back.
Kafka: nothing published.
Outbox: nothing to publish.
System is clean. No orphaned event. ✅
```

**Scenario B: Service crashes after commit, before Kafka publish**

```
BEGIN transaction
INSERT INTO orders ...  ✅
INSERT INTO outbox ...  ✅
COMMIT                  ✅
--- SERVICE CRASHES HERE 💥 ---

Outbox processor (on restart or separate pod):
Reads outbox: finds unpublished entry for order #5678
Publishes to Kafka ✅
Marks as published ✅

Result: Event is eventually published despite the crash. ✅
```

**Scenario C: Kafka is down for 5 minutes**

```
Order Service: inserts order + outbox entry → commits ✅

Outbox Processor:
Attempt 1: Kafka is down → publish fails → leave published=false, retry
Attempt 2: Kafka still down → retry
Attempt 3: Kafka still down → retry
...5 minutes later...
Attempt N: Kafka recovered → publish succeeds ✅ → published=true

Result: Event is published as soon as Kafka recovers.
Orders that came in during the outage are all processed. ✅
```

This is the power of the Outbox: **your application is decoupled from Kafka's availability.** Orders are accepted regardless of whether Kafka is up. Events catch up when Kafka recovers.

---

### ⚠️ The Outbox Does NOT Give You Exactly-Once

Here's the misconception that trips up everyone:

> "Great, Outbox solves everything. Events are reliably published. We're done."

Not quite. The outbox processor has its own dual write problem:

```
Outbox Processor:

Step 1: Publish event to Kafka       ✅
Step 2: UPDATE outbox SET published=true  💥 (DB blip)

Next loop iteration:
Step 1: Event is still published=false in outbox
Step 2: Publishes to Kafka AGAIN 💥 (duplicate!)

Consumer sees: OrderPlaced for order #5678 TWICE
```

This is guaranteed to happen. Not "might happen" - will happen, under load, in production.

The Outbox gives you **at-least-once delivery**, not exactly-once. This is fine and expected. The solution is not to fix the Outbox - it's to make consumers idempotent.

---

### 🔁 Idempotent Consumers: The Other Half of the Solution

An idempotent consumer processes the same event multiple times with the same outcome as processing it once. The combination is:

```
Transactional Outbox → guarantees at-least-once delivery
Idempotent Consumers → makes at-least-once effectively exactly-once

Together: reliable, duplicate-safe event processing
```

The implementation pattern: every event carries a unique ID. Consumers track which event IDs they've processed. On receiving an event, check first.

```
Event arrives: { eventId: "evt-abc-789", type: "OrderPlaced", orderId: "5678" }

Consumer:
  1. Check: processed_events table contains "evt-abc-789"?
     YES → skip processing, commit Kafka offset, done (idempotent no-op)
     NO  → continue

  2. Process the event (reserve inventory, charge payment, etc.)

  3. In ONE local transaction:
     INSERT INTO processed_events (event_id) VALUES ("evt-abc-789")
     [your business operation - e.g., UPDATE inventory SET stock -= 1]

  4. Commit Kafka offset
```

The critical point: recording the event ID and doing the business operation must be in the **same local ACID transaction**. Otherwise you recreate the dual write problem at the consumer side.

---

### 🧠 Mental Model: Outbox + Idempotency

> **The Outbox is a "to-do list" for events.** You write your task (the order) and your reminder (the outbox entry) in the same notebook at the same time. A separate assistant reads the reminder list and makes the phone calls (publishes to Kafka). If the assistant calls twice by mistake, the recipient (consumer) checks their call log and says "already handled this one, ignoring." The notebook guarantees nothing is forgotten. The call log guarantees nothing is done twice.

---

### 🔄 Polling vs Change Data Capture

There are two ways for the Outbox processor to detect new entries:

**Polling:** A scheduled job queries `SELECT * FROM outbox WHERE published = false` every N milliseconds. Simple, works everywhere, but adds DB load and introduces latency proportional to the poll interval.

**Change Data Capture (CDC):** Tools like Debezium tail the database's write-ahead log (WAL). Every INSERT to the outbox table is streamed in real-time to Kafka without polling. Zero application-side polling, sub-second latency, no additional DB load. More complex to set up. Used by LinkedIn, Uber, and many large-scale systems.

| Approach       | Latency   | DB Load  | Complexity | Used When                      |
| -------------- | --------- | -------- | ---------- | ------------------------------ |
| Polling        | 100ms–5s  | Moderate | Low        | Smaller scale, simpler ops     |
| CDC (Debezium) | Sub-100ms | Very low | Higher     | High scale, low latency needed |

---

### 💬 Interview Questions - Outbox + Idempotency

**"How do you ensure an event is published to Kafka even if your service crashes?"**
Transactional Outbox: write event to an outbox table in the same DB transaction as your business data. A separate processor publishes from the outbox. Crashes before the processor runs leave the outbox entry unpublished=false, so it's retried on recovery.

**"Why doesn't the Transactional Outbox guarantee exactly-once delivery?"**
The processor publishes to Kafka and then marks the row as published. If it crashes between those two steps, it re-publishes on restart, causing a duplicate. At-least-once is the correct characterization. Exactly-once requires idempotent consumers.

**"What is the difference between the producer-side Outbox and the consumer-side idempotency check?"**
Outbox is a producer pattern ensuring no event is lost. Idempotency is a consumer pattern ensuring no event causes duplicate side effects. Both are needed. Outbox without idempotency = duplicate effects. Idempotency without Outbox = risk of lost events.

## 🔥 Part 2: Retry, Backoff, and Circuit Breakers - Managing Downstream Failures

### The Scene: Your Service Calls Another Service

Your Payment Service needs to call the bank's payment gateway to charge a card. The gateway is an external HTTP service. What can go wrong?

```
Payment Service ──HTTP──► Bank Payment Gateway

Failure modes:
  Gateway is restarting (30-second window) → 503 Service Unavailable
  Gateway is overloaded → 429 Too Many Requests
  Network is congested → Timeout (no response within N seconds)
  Gateway has a bug in one code path → 500 Internal Server Error
  Gateway is totally down → Connection refused
```

Almost all of these are **transient** - temporary conditions that self-resolve. The right response is to **retry**. But retry naively and you create new disasters.

---

### 🚫 Naive Retry: How to Take Down a Recovering Service

Imagine the bank gateway went down at 10:00 AM. By 10:00:05 it starts recovering. But your 10,000 concurrent users all got errors, and all of them are retrying simultaneously:

```
10:00:00 - Gateway goes down
10:00:01 - 10,000 requests hit gateway → all fail
10:00:02 - All 10,000 retry immediately → all fail
10:00:03 - All 10,000 retry immediately → all fail
10:00:04 - All 10,000 retry immediately → all fail
10:00:05 - Gateway starts to recover
10:00:05 - 10,000 requests HIT IT SIMULTANEOUSLY 💀
          → Gateway is overwhelmed before it can stabilize
          → Gateway crashes again
10:00:10 - Gateway tries to recover again
          → 10,000 retries hit it again
          → Crashes again
          → This loops forever
```

This is called a **Retry Storm** or **Thundering Herd**. Your well-intentioned retries are the reason the service can never recover. The cure is worse than the disease.

---

### ⏰ Exponential Backoff: Spacing Out Retries

The fix: each retry waits exponentially longer than the previous one.

```
Attempt 1: fails → wait 1 second
Attempt 2: fails → wait 2 seconds
Attempt 3: fails → wait 4 seconds
Attempt 4: fails → wait 8 seconds
Attempt 5: fails → wait 16 seconds
...
Max wait cap: 60 seconds (don't wait forever between retries)
Max attempts: 5 (don't retry forever)
```

Exponential backoff gives the recovering service **breathing room**. Requests trickle back in rather than flooding all at once.

But there's still a problem. If 10,000 clients all start retrying at the exact same second and all back off by the same schedule, they still synchronize. They all retry at t=1, t=3, t=7, t=15 simultaneously.

---

### 🎲 Jitter: Randomizing the Retry Schedule

Add randomness (jitter) to desynchronize clients:

```
WITHOUT JITTER (synchronized):
Client 1: retries at 1s, 2s, 4s, 8s
Client 2: retries at 1s, 2s, 4s, 8s
Client 3: retries at 1s, 2s, 4s, 8s
→ All hit the service at the same moment every time

WITH JITTER (desynchronized):
Client 1: retries at 0.7s, 1.9s, 3.2s, 7.8s
Client 2: retries at 1.1s, 2.4s, 4.7s, 8.3s
Client 3: retries at 0.9s, 1.6s, 3.9s, 9.1s
→ Spread across time, service gets gentle trickle
```

The formula: `wait = base_delay * (2^attempt) * random(0.5, 1.5)`

"Full jitter" (AWS's recommended approach): `wait = random(0, base_delay * 2^attempt)`

This is **exponential backoff with jitter** - the industry standard retry strategy for any network call.

---

### 🔑 What Is Retryable vs Non-Retryable?

Not all failures should be retried. Retrying the wrong errors wastes time and makes things worse.

| HTTP Status               | Meaning                     | Retry?               | Why                                                  |
| ------------------------- | --------------------------- | -------------------- | ---------------------------------------------------- |
| 400 Bad Request           | Your request is malformed   | ❌ Never             | Retrying same malformed request → same error forever |
| 401 Unauthorized          | Not authenticated           | ❌ Never             | Auth won't fix itself by retrying                    |
| 403 Forbidden             | No permission               | ❌ Never             | Permissions don't change mid-request                 |
| 404 Not Found             | Resource doesn't exist      | ❌ Usually not       | Resource won't appear by retrying                    |
| 408 Request Timeout       | Server timed out processing | ✅ Yes               | Likely transient load spike                          |
| 429 Too Many Requests     | Rate limited                | ✅ Yes, with backoff | Respect Retry-After header                           |
| 500 Internal Server Error | Server bug/crash            | ✅ Sometimes         | May be transient; respect idempotency                |
| 502 Bad Gateway           | Upstream failure            | ✅ Yes               | Infrastructure issue, usually transient              |
| 503 Service Unavailable   | Service down/overloaded     | ✅ Yes, with backoff | Classic transient failure                            |
| 504 Gateway Timeout       | Upstream timeout            | ✅ Yes               | Network/infrastructure issue                         |

**The golden rule:** Only retry on errors that are transient AND where the operation is idempotent (or you can guarantee it hasn't partially executed).

Never retry a payment charge without an idempotency key. If the request timed out, you don't know if it succeeded on the server side. Retry without idempotency = potential double charge.

---

### ⚡ Circuit Breaker: Failing Fast When the Service Is Clearly Down

Exponential backoff with jitter handles transient failures well. But what about non-transient failures? What if the bank gateway is down for 3 hours?

Without a circuit breaker:

```
10:00 AM - Gateway goes down
10:00–1:00 PM - Your Payment Service dutifully retries every request
               → Every payment attempt takes 30 seconds to time out
               → 30 seconds × 10,000 requests = threads exhausted
               → Your Payment Service's thread pool is 100% occupied
                  waiting for timeouts
               → New requests can't be handled → Payment Service is slow
               → Cascading failure: Order Service times out on Payment
               → Order Service goes down
               → Your entire checkout is dead 💀
```

This is **cascading failure through synchronous coupling**. One downstream service being down takes down everything above it.

The circuit breaker pattern short-circuits this cascade.

---

### 🔌 Circuit Breaker: Three States

Think of it like an electrical circuit breaker. When too much current flows (too many failures), the breaker trips and cuts the circuit before wires catch fire.

```
                  ┌─────────────────────────────────┐
                  │         CIRCUIT BREAKER          │
                  │                                  │
   ┌──────────────▼──────────────┐                  │
   │          CLOSED             │  (normal operation)
   │  Requests pass through      │
   │  Tracking failure rate      │
   └──────────────┬──────────────┘
                  │ failure rate > threshold
                  │ (e.g., >50% in last 60s)
                  ▼
   ┌──────────────────────────────┐
   │           OPEN               │  (failing fast)
   │  ALL requests fail immediately│
   │  No calls to downstream       │
   │  Wait for recovery timeout    │
   └──────────────┬───────────────┘
                  │ timeout expires (e.g., 30 seconds)
                  ▼
   ┌──────────────────────────────┐
   │        HALF-OPEN             │  (probing for recovery)
   │  Let ONE request through     │
   │  If it succeeds → CLOSED     │
   │  If it fails → OPEN again    │
   └──────────────────────────────┘
```

**CLOSED state** (normal): All requests pass through to the downstream service. The circuit breaker monitors success/failure rates. If the failure rate crosses a threshold (say, 50% failures in a rolling 60-second window), the breaker trips to OPEN.

**OPEN state** (tripped): All requests **fail immediately** without even trying the downstream service. Your service instantly returns an error (or a fallback response). No threads are wasted waiting for timeouts. No cascading delays.

**HALF-OPEN state** (probing): After a recovery timeout (say, 30 seconds), the circuit breaker allows a single test request through. If it succeeds, the circuit closes (full traffic resumes). If it fails, it goes back to OPEN and waits another 30 seconds.

---

### ⚔️ Retry vs Circuit Breaker: They Work Together, Not Against Each Other

A common confusion: "If I have a circuit breaker, do I still need retry?"

Yes. They solve different problems:

| Mechanism       | Handles                            | How                      |
| --------------- | ---------------------------------- | ------------------------ |
| Retry + Backoff | Short transient failures (seconds) | Waits and tries again    |
| Circuit Breaker | Sustained failures (minutes/hours) | Stops trying, fails fast |

**Together:**

```
Request fails →
  Is it retryable? YES →
    Retry with exponential backoff + jitter
    Still failing after 3-5 attempts?
      Circuit breaker is tracking these failures
      Failure rate crosses threshold?
        Circuit OPENS → all subsequent requests fail immediately
        After 30s, circuit HALF-OPENS → test request
        Test succeeds → circuit CLOSES → retries work again
```

Retry handles the 30-second blip. Circuit breaker handles the 3-hour outage.

---

### 🏥 Fallback Strategies: What to Do When Circuit Is Open

When the circuit is open, you have options beyond "just fail":

**Return cached data:** "The recommendations service is down. Return last-cached recommendations from 5 minutes ago." Netflix does this - a user sees yesterday's recommendations rather than an error.

**Return a safe default:** "The fraud-detection service is down. Approve orders under $100 (low risk), reject orders over $1,000 (high risk without scoring), queue orders between $100-$1,000 for review."

**Degrade gracefully:** "The inventory service is down. Show the product without a real-time stock count. Let users add to cart; handle stock conflicts at checkout."

**Queue for later:** "The email service is down. Accept the request, queue the email, send when service recovers."

The pattern: **design for partial functionality** rather than all-or-nothing. A shopping experience with degraded personalization is better than a 500 error.

---

### 🧠 Mental Model: Retry + Circuit Breaker

> **Retry is a persistent employee who keeps trying to open a jammed door.** First attempt: shove harder. Second attempt: wait a minute and try again. Third attempt: wait 4 minutes. This makes sense for a briefly stuck door.
>
> **Circuit Breaker is a security system that realizes the door isn't stuck - the building is on fire.** Once enough people have tried and failed, the system stops letting anyone near the door, posts a "DO NOT ENTER" sign, and only lets one person test it again after the fire department has had time to respond.
>
> Together: try the door a few times (retry). If it's clearly a building fire (breaker trips), stop sending people to the door. Once fire is out (breaker probes), cautiously let traffic through again.

---

### 💬 Interview Questions - Retry + Circuit Breaker

**"How would you prevent your service from being brought down by a slow dependency?"**
Circuit breaker with a timeout. Set aggressive timeouts on all downstream calls. Track failure rates. When threshold exceeded, open the circuit and return fallback responses. No threads blocked waiting for a broken service.

**"When does retry make things worse?"**
When the downstream service is overloaded (retries add more load), when failures are not transient (retrying a bad request forever), when the operation is not idempotent (retrying a charge without idempotency key), and when there's no backoff (retry storms on recovery).

**"What's the difference between a timeout and a circuit breaker?"**
A timeout limits how long a single request waits. A circuit breaker tracks patterns across many requests and stops making calls entirely when a dependency is clearly failing. Timeouts prevent individual request hangs; circuit breakers prevent cascading failures.

## 🌊 Part 3: Backpressure - When Producers Outrun Consumers

### The Scene: YouTube Video Upload Processing

When you upload a video to YouTube, many things need to happen: transcoding to multiple resolutions, thumbnail extraction, content ID scanning for copyright, metadata indexing, CDN distribution. These are expensive, time-consuming operations.

During normal hours: 500 videos uploaded per minute, processing pipeline handles 600 per minute. No problem.

During peak hours: 5,000 videos uploaded per minute (everyone uploading after big events). Processing pipeline still handles 600 per minute.

What happens to the other 4,400 videos per minute?

---

### 📈 Consumer Lag: The Warning Sign

In Kafka, consumer lag is the difference between the latest offset produced and the latest offset consumed by a consumer group.

```
"video-uploads" Kafka topic:

Producer offset (latest message):  offset = 50,000
Consumer offset (latest processed): offset = 12,000

Consumer lag = 50,000 - 12,000 = 38,000 messages behind

This means: 38,000 uploaded videos are waiting to be processed.
At 600 videos/minute, it will take 63 minutes to catch up.
But new videos are arriving at 5,000/minute.
The lag is growing, not shrinking. 💀
```

Consumer lag that grows indefinitely means your system cannot keep up. Eventually:

- Memory fills up buffering unconsumed messages
- Processing delay grows unboundedly (video uploaded at 2 PM still processing at midnight)
- Users complain their videos aren't "processing"
- If the queue has a maximum size, producers start getting rejected

---

### 🔄 Backpressure: The Consumer Telling the Producer to Slow Down

Backpressure is the mechanism by which a system communicates upstream that it's overwhelmed, causing upstream components to slow down or stop until downstream catches up.

```
WITHOUT BACKPRESSURE:

Upload Service (producer)
    │ 5,000 videos/min
    ▼
Message Queue
    │ filling up, lag growing
    ▼
Processing Service (consumer)
    │ 600 videos/min
    ▼
    💀 Queue overflows, messages dropped
       or
    💀 Consumer OOMs trying to buffer

WITH BACKPRESSURE:

Upload Service (producer)
    │ asks queue: "how full are you?"
    ▼
Message Queue
    │ "I'm 80% full, slow down!"
    ▼
Upload Service: throttles to 600 videos/min
    │ consumer can keep up now
    ▼
Processing Service (consumer)
    │ 600 videos/min
    ▼
    ✅ Stable system
```

---

### 🎮 Backpressure Mechanisms in Practice

**Mechanism 1: Queue depth monitoring + producer throttling**

Producer checks queue depth before publishing. If queue is above a threshold, producer slows down or rejects new requests with a 429 (Too Many Requests), letting clients retry later.

**Mechanism 2: Kafka consumer lag monitoring**

Your operations team monitors consumer lag via Kafka metrics. Alerts fire when lag exceeds a threshold. Response: scale up consumer instances (add more pods in Kubernetes). Since Kafka partitions limit parallelism, you may need to increase partition count first.

```
Consumer lag alert: lag > 10,000 messages
Action: Scale consumer group from 4 instances to 12 instances
Result: Throughput triples, lag starts decreasing

But: "orders" topic has 4 partitions
     12 consumers → 8 are idle (more consumers than partitions)
     Real action: increase partitions to 12 first, THEN scale consumers
```

**Mechanism 3: Bounded queues with rejection**

Instead of an unbounded queue, define a maximum size. When full, new producers receive explicit backpressure (queue full error). Producers must handle this by slowing down, retrying with backoff, or queuing locally.

**Mechanism 4: Rate limiting at the API gateway**

The simplest backpressure: reject requests at the edge before they enter the system. Return 429 with a Retry-After header. Clients back off. System protects itself.

---

### ⚖️ The Three Outcomes When Producer > Consumer

| Response       | What Happens                              | Use When                              |
| -------------- | ----------------------------------------- | ------------------------------------- |
| Drop messages  | Exceeding messages are discarded          | Metrics, logs, non-critical analytics |
| Block producer | Producer waits until consumer catches up  | Real-time systems, streaming          |
| Buffer (queue) | Messages stored, consumer processes later | Most async systems; lag is acceptable |

For an order processing system: you never drop orders. You buffer in Kafka (which is designed for this) and process in order. The trade-off is increased latency during peak load, which is acceptable if bounded.

For a metrics/logging system: dropping samples when overwhelmed is fine. A 1% sampling loss in metrics is invisible. Blocking the entire system because of metrics overflow is not acceptable.

---

### 🎯 Consumer Scaling Strategies

When consumer lag grows, here's how to respond:

```
STRATEGY 1: Scale out consumers (horizontal scaling)
  Add more consumer instances
  Requires: enough partitions to support parallelism
  Best for: processing that's CPU/IO bound and stateless

STRATEGY 2: Optimize consumer processing
  Profile the consumer: what's slow?
  Database calls? → batch them, add indexes
  External API calls? → parallelize with async processing
  Heavy computation? → use more efficient algorithms

STRATEGY 3: Partition your topic better
  If key distribution is uneven, some partitions are hot
  One consumer is overwhelmed while others are idle
  Solution: choose a better partition key (more evenly distributed)

STRATEGY 4: Increase partition count
  More partitions = more parallel consumers
  But: cannot decrease partitions later; requires consumer rebalancing

STRATEGY 5: Tiered processing
  Fast lane: simple events processed immediately
  Slow lane: complex events (video transcoding) in a separate topic
  Don't let heavy processing block lightweight processing
```

### 🌊 Reactive Systems and Backpressure

Modern reactive frameworks (Project Reactor, RxJava, Akka Streams) build backpressure into the programming model. A consumer explicitly signals how many items it can handle, and the producer only emits that many.

The mental model: instead of a firehose (producer pushes as fast as it can), it's a pull-based system (consumer asks for items at its own pace). This is elegant in code but complex to reason about in large distributed systems.

---

### 🧠 Mental Model: Backpressure

> **Backpressure is like a highway on-ramp metering light.** During traffic jams, the traffic management system turns on red lights on freeway on-ramps, allowing only one car per green light to enter. Cars back up on the on-ramp. The highway doesn't collapse trying to absorb everyone at once. When traffic clears, the lights go green more frequently. The pain (waiting on the ramp) is pushed back to the source (individual cars) rather than causing a systemic collapse (gridlock on the whole freeway).
>
> Without backpressure: everyone enters the freeway at once → gridlock → everyone is slow.
> With backpressure: on-ramp queues, freeway stays free → queued cars enter steadily → same total cars, better total throughput.

### 💬 Interview Questions - Backpressure

**"YouTube receives 500 hours of video every minute. How does the processing pipeline avoid being overwhelmed?"**
Kafka as the buffer between upload service and processing pipeline. Consumer lag monitoring with automated scaling. Tiered processing (quick metadata extraction vs. expensive transcoding in separate consumer groups). Rate limiting at the upload API. Priority queues for paid creators vs. free tier.

**"What happens if your Kafka consumer can't keep up with the producer?"**
Consumer lag grows. If bounded retention, old events start getting deleted before processing (data loss). Mitigation: monitor lag with alerts, auto-scale consumers, increase partitions, optimize consumer throughput, rate limit producers.

**"What is the difference between rate limiting and backpressure?"**
Rate limiting is a hard cap applied by the system to all clients (e.g., 100 requests/minute per user). Backpressure is a signal from a downstream component to an upstream component to slow down based on current capacity. Rate limiting is policy; backpressure is a feedback mechanism.

```

      ├── Validates request
      ├── BEGIN local transaction

        Attempt 2: Warehouse API → 503 (still restarting)

        Attempt 3: Warehouse API → 200 ✅

      (Not enough to trip - threshold might be 50% in 60s window)

        Circuit breaker: tracking failures...
        Attempt 2: Gateway → 503                          ← RETRY

        Circuit is now OPEN:
        Next 50 payment requests all fail immediately (< 1ms)
        No threads blocked waiting for 28-second timeouts

        Fallback: Queue payment for retry, return OrderPendingPayment status
```

## 🗂️ Part 5: Failure Recovery - What Happens When Everything Is Already Broken

### Idempotent Replay: The Most Powerful Recovery Tool

Because your outbox preserves events and your consumers are idempotent, you have an extraordinary superpower: **you can replay any event from any point in time and the system will converge to the correct state.**

```
Scenario: Analytics Service had a bug for 3 hours.
          Processed 50,000 events incorrectly.
          Bug is fixed and deployed.

Recovery:
1. Seek consumers in analytics-group to offset 3 hours ago
2. Set published=false for all outbox entries in that window
   OR just replay directly from Kafka (which retains events)
3. Re-process 50,000 events with the fixed code

Result: Analytics data is correct again.
Time: Hours, not days.
Risk: Zero, because idempotent consumers don't cause duplicate effects.
```

Without idempotency: replaying is terrifying. You might double-charge customers, send duplicate emails, apply discounts twice. You might not replay at all, leaving corrupted data in place.

With idempotency: replay is routine. It's how you recover from almost any bug.

---

### Dead Letter Queue: The Last Line of Defense

When all retries are exhausted and the circuit has opened and closed multiple times, some events still can't be processed. These go to the Dead Letter Queue.

```
"orders" topic event arrives at Payment Service consumer
  Retry 1: fails
  Retry 2: fails
  Retry 3: fails
  Max retries exhausted

  → Event published to "orders-dlq" topic
  → Consumer commits offset (moves on - doesn't block!)
  → DLQ monitor detects new entry → pages on-call engineer

Engineer investigates:
  Was it a bug? Fix it, replay from DLQ back to "orders" topic
  Was it bad data? Mark as permanently failed, notify user
  Was it infrastructure? Replay after infra recovers
```

The DLQ provides **visibility into what the system couldn't handle** and a **way to recover without losing the event**. Events in the DLQ are not lost - they're isolated, awaiting human judgment.

---

### Saga State Persistence: Recovering Long-Running Workflows

Sagas can run for minutes (order processing) or hours (loan approval). The state machine must survive crashes.

```
Saga State Table:

┌──────────┬─────────────────────┬─────────────┬──────────────────────┐
│ saga_id  │ current_step        │ status      │ last_updated         │
├──────────┼─────────────────────┼─────────────┼──────────────────────┤
│ S-001    │ RESERVE_INVENTORY   │ IN_PROGRESS │ 2024-01-15 10:30:01  │
│ S-002    │ CHARGE_PAYMENT      │ IN_PROGRESS │ 2024-01-15 10:31:45  │
│ S-003    │ COMPLETED           │ DONE        │ 2024-01-15 10:29:12  │
└──────────┴─────────────────────┴─────────────┴──────────────────────┘
```

If the orchestrator crashes, on restart it queries for all IN_PROGRESS sagas and resumes from the last committed step. This requires that each step is idempotent - resuming a step that was partially executed must be safe.

A watchdog process monitors sagas that haven't progressed in N minutes and pages the on-call team (or automatically attempts recovery). Sagas that are stuck are often more dangerous than sagas that failed - a failed saga is known; a stuck saga is silently wrong.

## 📊 Part 6: Complete Reliability Pattern Reference

### When to Apply Each Pattern

| Pattern                | Problem It Solves                                      | When You Need It                                    |
| ---------------------- | ------------------------------------------------------ | --------------------------------------------------- |
| Transactional Outbox   | DB succeeds, event lost                                | Any time you write to DB + publish event            |
| Idempotent Consumer    | Duplicate event = duplicate effect                     | Any at-least-once delivery system                   |
| Retry + Backoff        | Transient downstream failure                           | All network calls to external services              |
| Jitter                 | Retry storm on recovery                                | Any system with >1 concurrent client                |
| Circuit Breaker        | Cascading failure from slow/down dependency            | Any synchronous downstream dependency               |
| Fallback Response      | Service still needs to respond when dependency is down | User-facing services with non-critical dependencies |
| DLQ                    | Events that can never be processed                     | All Kafka consumers with retry logic                |
| Backpressure           | Consumer lag growing unboundedly                       | Any producer-consumer system at scale               |
| Saga + Compensation    | Multi-service workflow consistency                     | Any cross-service business workflow                 |
| Saga State Persistence | Long-running workflow survives crash                   | Sagas running longer than minutes                   |

### The Common Misconceptions

❌ **"Transactional Outbox gives exactly-once delivery"**
✅ It gives at-least-once. The outbox processor might publish an event, then crash before marking it published, causing re-publication. Exactly-once requires idempotent consumers on the receiving end.

❌ **"Retry always helps"**
✅ Retry helps for transient failures. For non-transient failures or non-idempotent operations, retry causes more harm. Always distinguish retryable (5xx, timeouts) from non-retryable (4xx, business logic failures).

❌ **"Circuit breaker replaces retry"**
✅ They're complementary. Retry handles short transient failures (seconds). Circuit breaker handles sustained failures (minutes/hours). Use both: retry a few times, and if failure rate is high, open the circuit.

❌ **"More Kafka consumers always fixes consumer lag"**
✅ You can have at most as many active consumers as partitions. Extra consumers are idle. To scale beyond current partition count, you must increase partitions first - which causes a rebalance and has its own considerations.

❌ **"Dead letter queue means the message is lost"**
✅ DLQ is the opposite of lost. The message is preserved, isolated, and awaiting human intervention. Lost means the message is gone and you don't know it failed.

❌ **"Idempotency means the operation runs only once"**
✅ Idempotency means running the operation multiple times produces the same result as running it once. The operation may run multiple times - it just doesn't cause duplicate effects. The implementation (unique constraints, processed_events table) is what prevents duplicates.

❌ **"Backpressure is only a Kafka/streaming concern"**
✅ Backpressure exists in any producer-consumer system: HTTP load balancers, database connection pools, thread pools. Any time producers can outpace consumers, you need a strategy. The mechanisms differ, but the problem is universal.
