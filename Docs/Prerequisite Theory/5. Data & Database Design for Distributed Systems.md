## 🧭 Part 1: Domain Modelling - Finding the Entities That Matter

### Start With the Business, Not the Database

Junior engineers open their IDE and start creating tables. Experienced engineers open a whiteboard and start asking questions about the **business**.

Domain modelling is the process of discovering the concepts, relationships, and boundaries in a business domain **before** writing any schema. Get this wrong and no amount of clever indexing or locking will save you.

### The Technique: Event Storming (Simplified)

Ask: **"What happens in this system?"** Write down every significant business event in past tense:

```
Amazon Order Processing:

Business Events:
  OrderPlaced
  PaymentProcessed
  PaymentFailed
  InventoryReserved
  InventoryReleased
  OrderShipped
  OrderDelivered
  OrderCancelled
  ReturnRequested
  RefundIssued
```

From events, **work backwards** to find the entities that cause them and the entities they affect:

```
OrderPlaced          → needs: Customer, Order, OrderItem, Product
PaymentProcessed     → needs: Payment, Order, CreditCard
InventoryReserved    → needs: Inventory, Product, Order
OrderShipped         → needs: Shipment, Order, Address, Carrier
ReturnRequested      → needs: Return, Order, OrderItem
RefundIssued         → needs: Refund, Payment
```

Now you have your candidate entities. But how do they relate?

### 🔍 Finding Bounded Contexts: Where to Draw the Lines

Not all entities belong together. The key question: **which entities change together and which change independently?**

```
SIGNAL 1: Different teams own them
  The team managing inventory doesn't need to know about
  payment gateway references. Different concerns.

SIGNAL 2: Different change rates
  Product catalog changes slowly (new items added occasionally).
  Inventory changes constantly (every purchase, return, restock).
  Separating them lets each evolve at its own rate.

SIGNAL 3: Different scaling needs
  Orders: moderate write rate, complex queries
  Inventory: very high write rate (every purchase), simple queries
  Payments: high security requirements, audit trail critical

SIGNAL 4: Different consistency requirements
  Order + OrderItems must always be consistent (same DB, ACID)
  Order + Payment can be eventually consistent (different services)
```

The result - our **bounded contexts** (which become our microservices):

```
┌─────────────────────────────────────────────────────────────────┐
│                    BOUNDED CONTEXTS                              │
│                                                                  │
│  ┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐ │
│  │  ORDER CONTEXT  │  │INVENTORY CONTEXT│  │ PAYMENT CONTEXT │ │
│  │─────────────────│  │─────────────────│  │─────────────────│ │
│  │ Order           │  │ Inventory       │  │ Payment         │ │
│  │ OrderItem       │  │ Product(ref)    │  │ Refund          │  │
│  │ Customer        │  │ Warehouse       │  │ CreditCard      │ │
│  │ Address         │  │ StockMovement   │  │                 │ │
│  └─────────────────┘  └─────────────────┘  └─────────────────┘ │
│                                                                  │
│  ┌─────────────────┐  ┌─────────────────┐                      │
│  │CATALOG CONTEXT  │  │SHIPPING CONTEXT │                      │
│  │─────────────────│  │─────────────────│                      │
│  │ Product         │  │ Shipment        │                      │
│  │ Category        │  │ Carrier         │                      │
│  │ ProductImage    │  │ TrackingEvent   │                      │
│  └─────────────────┘  └─────────────────┘                      │
└─────────────────────────────────────────────────────────────────┘
```

Notice: **Product** appears in multiple contexts. That's normal. Each context has its own view of a Product - the Inventory context cares about SKU and stock level, the Catalog context cares about description and images, the Order context cares about price at time of purchase. They're the same real-world thing but represented differently in each context.

### ⚠️ The Most Common Domain Modelling Mistakes

**Mistake 1: Anemic domain model**
Entities are just data bags (getters/setters). All logic lives in service classes. Result: business rules scattered everywhere, easy to violate invariants.

```
BAD - anemic:
Order entity: just id, status, items, total
OrderService: 500-line class with all order logic

BETTER - rich domain:
Order entity: has placeOrder(), cancel(), addItem(), calculateTotal()
Business rules are enforced by the entity itself
```

**Mistake 2: Database-first thinking**
Designing tables before understanding business events. Results in schemas that map to technical structure, not business concepts.

**Mistake 3: Shared mutable state between contexts**
Two services reading and writing the same column in the same table. Changes to that column require coordinating two teams. Schemas can't evolve independently.

**Mistake 4: Skipping the "what's the invariant?" question**
Every entity has rules that must always hold. Order total must equal sum of item prices. Inventory quantity must never go below zero. Identifying these invariants upfront determines what data must be co-located in the same transaction boundary.

---

### 🧠 Mental Model: Domain Modelling

> **Domain modelling is like architectural blueprints before construction.** A contractor who starts building without blueprints will have to tear down walls when the plumbing doesn't fit. An engineer who creates tables before understanding the business will have expensive migrations when the schema needs to reflect reality. Blueprints (domain model) capture what the business actually does; implementation (schema) is the physical realization. Always blueprint first.

## 🗃️ Part 2: Database-Per-Service - Why Microservices Don't Share Databases

### The Tempting Shortcut

When you split a monolith into microservices, the laziest approach is to keep the single database and just have each service point to it. Services get deployed independently - job done, right?

```
THE TEMPTING SHORTCUT:

┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐
│  Order Service  │  │Inventory Service│  │ Payment Service │
└────────┬────────┘  └────────┬────────┘  └────────┬────────┘
         │                    │                     │
         └────────────────────┼─────────────────────┘
                              │
                    ┌─────────▼─────────┐
                    │   SHARED DATABASE  │
                    │   (one schema,     │
                    │    all tables)     │
                    └───────────────────┘
```

This looks harmless. It's not. Let's walk through exactly what goes wrong.

---

### 💥 What Actually Breaks With a Shared Database

**Problem 1: Schema changes require coordinating all teams**

```
Scenario: Inventory team needs to rename column
  `products.stock_count` → `products.available_quantity`

Who does this affect?
  Order Service: queries products table to check availability
  Catalog Service: displays stock status to users
  Analytics Service: reports on stock levels
  
Every team must update their code simultaneously.
One team is on vacation.
The migration is blocked for 3 weeks.

With database-per-service:
  Inventory Service owns its schema.
  Rename the column. Only your service needs updating.
  No coordination needed.
```

**Problem 2: One service's load kills everyone else**

```
Scenario: Black Friday - Analytics Service runs a massive
reporting query on the shared database:

SELECT p.name, SUM(oi.quantity) as units_sold, SUM(oi.unit_price * oi.quantity) as revenue
FROM order_items oi
JOIN products p ON oi.product_id = p.id
JOIN orders o ON oi.order_id = o.id
WHERE o.created_at BETWEEN '2024-11-29' AND '2024-11-30'
GROUP BY p.name
ORDER BY revenue DESC;

This query runs for 45 seconds, locks index scans on order_items,
causes I/O contention on the shared disk.

Effect on Order Service: inserts to order_items table are slow.
Checkout times spike from 200ms to 8 seconds.
Users abandon carts.
Revenue drops.

Cause: One service's analytical workload degraded transactional workload.

With separate databases: Analytics runs on its own read replica.
Order Service is completely unaffected.
```

**Problem 3: No independent scaling**

```
Inventory Service: receives 50,000 stock-decrement operations/second
                   on Black Friday. Needs a high-write-throughput DB
                   (maybe sharded, maybe NoSQL).

Order Service: complex multi-table queries, moderate write rate.
               Works perfectly on PostgreSQL.

Payment Service: needs strict ACID, full audit trail, never lose a record.
                 Financial-grade PostgreSQL with point-in-time recovery.

With shared database: must choose ONE database technology for all three
very different workloads. Compromise everywhere, optimal nowhere.

With database-per-service: each service picks the right tool:
  Inventory → Redis + PostgreSQL
  Orders    → PostgreSQL
  Payments  → PostgreSQL with enhanced durability
```

**Problem 4: Tight coupling defeats the purpose of microservices**

```
SHARED DB COUPLING:

Inventory Service and Order Service both join on:
  orders.product_id → inventory.product_id

Now you can't:
  Change the products table structure without coordinating
  Move inventory to a different database technology
  Deploy Inventory Service changes that alter the schema
  Scale Inventory independently (shared connection pool)
  
The microservices are as tightly coupled as the old monolith.
You got the operational complexity of microservices
with none of the flexibility.
```

---

### ✅ Database-Per-Service: The Correct Picture

```
┌─────────────────┐   ┌─────────────────┐   ┌─────────────────┐
│  Order Service  │   │Inventory Service│   │ Payment Service │
│                 │   │                 │   │                 │
│  Orders DB      │   │  Inventory DB   │   │  Payments DB    │
│  (PostgreSQL)   │   │  (PostgreSQL    │   │  (PostgreSQL    │
│  orders         │   │   + Redis)      │   │   strict ACID)  │
│  order_items    │   │  inventory      │   │  payments       │
│  customers      │   │  products       │   │  refunds        │
│  addresses      │   │  warehouses     │   │  audit_log      │
└─────────────────┘   └─────────────────┘   └─────────────────┘

Each database:
✅ Owned by one team
✅ Schema evolves independently
✅ Scaled independently
✅ Technology chosen for the workload
✅ Isolated failures (one DB slow doesn't affect others)
✅ Security boundaries (Payment DB credentials not shared)
```

---

### The Consequence: No Cross-Service Joins

With separate databases, you lose one thing: **SQL joins across services**.

```
WHAT YOU LOSE:
SELECT o.id, o.total, p.name, i.available_quantity
FROM orders o
JOIN order_items oi ON o.id = oi.order_id
JOIN inventory i ON oi.product_id = i.product_id  ← IMPOSSIBLE: different DB
JOIN products p ON i.product_id = p.id             ← IMPOSSIBLE: different DB

WHAT YOU DO INSTEAD:
Option 1: API composition
  Order Service fetches order data
  Calls Inventory Service API to get stock levels
  Calls Catalog Service API to get product names
  Composes the result in application code

Option 2: Materialized view / event-driven denormalization
  Order Service listens to ProductUpdated events
  Stores a local copy of product name in order_items.product_name_snapshot
  No cross-service join needed; data is co-located
  Trade-off: eventual consistency, some data duplication
  
Option 3: Separate read model (CQRS)
  A dedicated "query service" subscribes to events from all services
  Builds a denormalized read model optimized for queries
  Serves the complex read queries without cross-service joins
```

This is the fundamental trade-off: **operational independence vs query simplicity.** At scale, the independence is worth it. For simpler systems, it may not be.

---

### 🧠 Mental Model: Database-Per-Service

> **Each microservice's database is like a private filing cabinet.** Different departments (services) have their own cabinets. Payroll doesn't open Engineering's cabinet. If Payroll needs someone's tax information, they call HR on the phone (API call). This is slower than walking down the hall to read the file directly, but it means HR can reorganize their cabinet (migrate schema) without telling Payroll. It also means a fire in Engineering's storage room doesn't burn HR's records.

### 💬 Interview Questions - Domain Modelling + Database-Per-Service

**"Why can't two microservices share a database?"**
Schema coupling prevents independent evolution. Load interference prevents independent scaling. Technology lock-in prevents choosing the right DB per workload. Security boundaries are violated. The core principle of microservices - independent deployability - is defeated.

**"How do you handle reporting queries that need data from multiple services?"**
Three options: API composition (fetch from each service, compose in application), event-driven denormalization (maintain local copies via events), or a dedicated read model/data warehouse that aggregates events from all services into a queryable store.

**"How do you identify bounded contexts in a new system?"**
Event storming: list business events, find the entities that cause and are affected by them, group by team ownership, change rate, scaling needs, and consistency requirements. Entities that always change together belong in the same context.

## 📋 Part 3: Flyway and Database Migrations - Evolving Schemas Safely

### The "Just Let Hibernate Do It" Disaster

Spring Boot with Hibernate has a seductive property: `spring.jpa.hibernate.ddl-auto=update`. Set it and Hibernate automatically modifies your schema to match your entities.

In development: magic.
In production: terrifying.

```
What hibernate.ddl-auto=update does in production:

Monday: You add a new column `discount_percentage` to Order entity.
        Hibernate adds the column automatically on startup.
        No problem.

Tuesday: You rename `total` to `total_amount` in Order entity.
         Hibernate CANNOT rename columns.
         Hibernate sees: column `total` missing → doesn't know to rename it.
         Hibernate sees: column `total_amount` missing → ADDS it.
         Now you have both `total` (old, with data) and `total_amount` (new, empty).
         Your queries break. Data appears missing. 💥

Wednesday: You remove a field from the entity.
           Hibernate does NOTHING with existing data.
           Or worse: in create-drop mode, it DROPS AND RECREATES the table.
           Your production data is gone. 💀

What hibernate.ddl-auto=validate (the safe setting) does:
  Fails startup if schema doesn't match entity mappings.
  Forces you to manage schema separately.
  This is the right setting for production.
```

---

### 🛫 Flyway: Versioned, Repeatable, Auditable Schema Evolution

Flyway treats your database schema like source code: **every change is a versioned migration file, applied in order, tracked in the database, never modified after execution.**

```
Your migration files (in src/main/resources/db/migration/):

V1__create_orders_table.sql
V2__create_order_items_table.sql
V3__add_customer_email_index.sql
V4__add_payment_status_to_orders.sql
V5__create_payments_table.sql
V6__rename_total_to_total_amount.sql
V7__add_discount_percentage_column.sql
```

Flyway tracks which migrations have run in a table it manages:

```
flyway_schema_history table:
┌─────────────┬─────────────────────────────────┬──────────────┬──────────┐
│ installed_rank│ script                         │ checksum     │ success  │
├─────────────┼─────────────────────────────────┼──────────────┼──────────┤
│ 1           │ V1__create_orders_table.sql      │ 1234567890   │ true     │
│ 2           │ V2__create_order_items_table.sql │ 2345678901   │ true     │
│ 3           │ V3__add_customer_email_index.sql │ 3456789012   │ true     │
│ 4           │ V4__add_payment_status.sql       │ 4567890123   │ true     │
│ 5           │ V5__create_payments_table.sql    │ 5678901234   │ true     │
└─────────────┴─────────────────────────────────┴──────────────┴──────────┘
```

On application startup: Flyway checks which migrations haven't run, runs them in order, records them. Already-run migrations are never touched again. The checksum detects if someone tries to modify an already-applied migration (which would break the audit trail).

---

### ✍️ What Migrations Look Like in Practice

**Creating the orders table (V1):**

```sql
-- V1__create_orders_table.sql
CREATE TABLE orders (
    id          BIGSERIAL PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    status      VARCHAR(20) NOT NULL DEFAULT 'PENDING',
    total       DECIMAL(10, 2) NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

**Adding a column safely (V7):**

```sql
-- V7__add_discount_percentage_column.sql
ALTER TABLE orders 
ADD COLUMN discount_percentage DECIMAL(5, 2);
-- Nullable! Existing rows get NULL, not an error.
-- If you add NOT NULL without a default: migration fails on
-- non-empty tables because existing rows have no value.
```

**The rename problem - how to do it right (V6):**

```sql
-- V6__rename_total_to_total_amount.sql
-- WRONG: ALTER TABLE orders RENAME COLUMN total TO total_amount;
-- This breaks any currently running application instances
-- that still use the old column name!

-- RIGHT: The expand-contract pattern:
-- Step 1 (this migration): Add new column, copy data
ALTER TABLE orders ADD COLUMN total_amount DECIMAL(10, 2);
UPDATE orders SET total_amount = total;
ALTER TABLE orders ALTER COLUMN total_amount SET NOT NULL;

-- Deploy new application code that writes to BOTH columns
-- Then in a LATER migration (V8), drop the old column
-- once all instances are using the new name.
```

This **expand-contract pattern** is how you rename columns without downtime:

```
Phase 1 (migration V6): Add new column + copy data
Phase 2 (deploy): Application writes to both old + new column
Phase 3 (migration V8): Drop old column once all instances use new one

Zero downtime. Zero data loss. Fully rollbackable.
```

---

### 🚀 Zero-Downtime Migration Rules

| Operation | Safe? | How to Do It Safely |
|---|---|---|
| Add nullable column | ✅ Yes | Just add it; existing rows get NULL |
| Add NOT NULL column with default | ✅ Yes (modern DBs) | PostgreSQL 11+ fills existing rows |
| Add NOT NULL column, no default | ❌ No | Add nullable, backfill data, add NOT NULL constraint |
| Add index (non-unique) | ⚠️ Use CONCURRENTLY | `CREATE INDEX CONCURRENTLY` - doesn't lock table |
| Add index (unique) | ⚠️ Careful | Validates all existing data; use CONCURRENTLY |
| Rename column | ❌ Breaking | Expand-contract pattern over multiple deployments |
| Drop column still used by app | ❌ Dangerous | Deploy code changes first, then drop |
| Rename table | ❌ Breaking | Create new table, migrate data, update app, drop old |
| Change column type | ⚠️ Depends | Widening (INT→BIGINT) often safe; narrowing dangerous |

---

### 🧠 Mental Model: Flyway Migrations

> **Flyway is version control for your database.** Your Git repository tracks every code change with a commit hash and author. Flyway tracks every schema change with a migration file and checksum. You can see the entire history of your schema. You can reproduce any historical state. You can never accidentally re-apply a migration. Just as you wouldn't directly edit deployed bytecode in production, you don't manually run SQL against production - you commit a migration file and let the pipeline apply it.

---

### 💬 Interview Questions - Migrations

**"Why not use Hibernate's auto DDL update in production?"**
Hibernate can't rename columns or handle complex transformations. It has no audit trail. Multiple instances starting simultaneously can cause race conditions. There's no way to review and approve schema changes before they execute. Flyway provides versioning, history, team coordination, and rollback planning.

**"How do you add a NOT NULL column to a table with 100 million rows without downtime?"**
Expand-contract: first add the column as nullable, backfill existing rows in batches (to avoid lock contention), add a NOT NULL constraint (fast in PostgreSQL after backfill), then in the next deployment cycle tighten the constraint.

**"How do you handle Flyway migrations when you have multiple service instances starting simultaneously?"**
Flyway uses a database-level lock during migration. Only one instance runs migrations; others wait. Once migrations complete, all instances start normally. This is safe because migrations are idempotent by design.

## 🔍 Part 4: Indexes - How the Database Finds Your Data Fast

### First, How Does a Database Find Data Without an Index?

Imagine you have an orders table with 50 million rows. You run:

```sql
SELECT * FROM orders WHERE customer_id = 12345;
```

Without an index, the database does a **full table scan**: reads every single row, checks if `customer_id = 12345`, returns matches. On 50 million rows, this might take 30+ seconds and read gigabytes of data from disk.

With an index on `customer_id`, the database jumps directly to matching rows in milliseconds.

The question is: *how?*

---

### 🌳 The B-Tree Index: What's Actually Happening

The most common index type (the default in PostgreSQL, MySQL) is a **B-Tree** (Balanced Tree).

```
B-Tree index on orders.customer_id:

                    ┌──────────────┐
                    │  Root Node   │
                    │  [5000|10000]│
                    └──────┬───────┘
              ┌────────────┤
              │            │            │
    ┌─────────▼──┐  ┌──────▼─────┐  ┌──▼────────────┐
    │[1000|2500] │  │[6000|8000] │  │[11000|15000]  │
    └────────────┘  └─────┬──────┘  └───────────────┘
                          │
             ┌────────────┤
             │            │
    ┌────────▼───┐  ┌─────▼──────┐
    │ [6001|6500]│  │[7000|7500] │
    └────────────┘  └────────────┘
    (leaf nodes contain actual row pointers)
```

**Finding customer_id = 7200:**

```
1. Read root: 7200 > 5000, go right child → [6000|8000]
2. Read node: 6000 < 7200 < 8000, go middle → leaf range
3. Read leaf: find 7200, get row pointer (physical location on disk)
4. Fetch row from table using pointer

Total reads: 3-4 node reads instead of 50 million row reads.
Time: microseconds instead of seconds.
```

B-Trees stay balanced as data is inserted, so search time is always O(log N) regardless of data size.

---

### 🎯 When to Add an Index - The Decision Framework

**Questions to ask:**

```
1. Is this column in a WHERE clause frequently? → candidate
2. Is this column in a JOIN condition?          → strong candidate
3. Is this column in an ORDER BY?               → candidate
4. How selective is this column?
   - customer_id: highly selective (few rows per value) → great index
   - status (5 values for 50M rows): low selectivity → maybe not
   - is_deleted (true/false): very low selectivity → rarely useful
5. How often is this table written to?
   - Every index slows down INSERT/UPDATE/DELETE
   - High-write tables: index carefully, only what's needed
```

**The selectivity rule:**

```
orders table: 50 million rows

status column (values: PENDING, CONFIRMED, SHIPPED, DELIVERED, CANCELLED):
  PENDING:    5M rows (10%)
  CONFIRMED:  8M rows (16%)
  SHIPPED:    12M rows (24%)
  DELIVERED:  23M rows (46%)
  CANCELLED:  2M rows (4%)

SELECT * FROM orders WHERE status = 'DELIVERED';
→ Returns 23 million rows (46% of table)
→ Index on status: database might IGNORE it!
→ Reading 23M rows via index is SLOWER than a sequential scan
   (index has overhead; sequential scan reads pages sequentially, 
    which is fast for large portions of a table)

SELECT * FROM orders WHERE customer_id = 12345;
→ Returns ~10 rows for a typical customer
→ 10 rows / 50M rows = 0.00002% selectivity → PERFECT for index
```

### 🧪 Concrete Index Examples: Amazon Orders System

```sql
-- Table: 50 million orders
CREATE TABLE orders (
    id          BIGSERIAL PRIMARY KEY,      -- already indexed (PK)
    customer_id BIGINT NOT NULL,
    status      VARCHAR(20) NOT NULL,
    total       DECIMAL(10,2) NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL,
    updated_at  TIMESTAMPTZ NOT NULL
);

-- Query 1: "Show me all orders for customer 12345"
SELECT * FROM orders WHERE customer_id = 12345;
-- Without index: full scan of 50M rows, ~30s
-- Add:
CREATE INDEX idx_orders_customer_id ON orders(customer_id);
-- With index: 3-4 tree reads, ~1ms ✅

-- Query 2: "Show me all PENDING orders for customer 12345"
SELECT * FROM orders WHERE customer_id = 12345 AND status = 'PENDING';
-- Single-column index on customer_id works (filters to ~10 rows, then checks status)
-- Even better: composite index
CREATE INDEX idx_orders_customer_status ON orders(customer_id, status);
-- Uses customer_id to find rows, status already in index → no table lookup needed

-- Query 3: "Show me orders placed in the last 7 days, newest first"
SELECT * FROM orders WHERE created_at > NOW() - INTERVAL '7 days' ORDER BY created_at DESC;
-- Needs range scan on created_at, already in sort order
CREATE INDEX idx_orders_created_at ON orders(created_at DESC);
-- Index scan returns rows pre-sorted → no sort operation needed ✅

-- Query 4: "Are there any orders with this payment_reference?"
SELECT * FROM orders WHERE payment_reference = 'PAY-XYZ-789';
-- payment_reference is unique → unique index enforces data integrity AND provides fast lookup
CREATE UNIQUE INDEX idx_orders_payment_ref ON orders(payment_reference) WHERE payment_reference IS NOT NULL;
-- Partial index: only indexes non-null values (saves space if most are null)
```

---

### 💰 The Hidden Cost of Indexes

Every index you add has a cost that most developers underestimate:

```
WRITE AMPLIFICATION:

INSERT into orders table (no extra indexes):
  Write 1 row to orders table heap.
  Write 1 entry to primary key index.
  Total: 2 writes.

INSERT into orders table (4 extra indexes):
  Write 1 row to orders table heap.
  Write 1 entry to PK index.
  Write 1 entry to idx_orders_customer_id.
  Write 1 entry to idx_orders_customer_status.
  Write 1 entry to idx_orders_created_at.
  Write 1 entry to idx_orders_payment_ref.
  Total: 6 writes.

On 50,000 order inserts per second: 
  Without extra indexes: 100,000 disk writes/second
  With 4 extra indexes:  300,000 disk writes/second

Indexes also:
  Consume disk space (large tables → large indexes)
  Must be locked during updates (though modern DBs minimize this)
  Slow down UPDATE statements that touch indexed columns
  Increase backup size and time
```

**The discipline:** index for your actual query patterns. Don't index everything "just in case." Use `EXPLAIN ANALYZE` to see which queries are slow and why, then add targeted indexes.

---

### 🧠 Mental Model: Index

> **An index is like a book's index at the back.** Without it, finding every mention of "circuit breaker" means reading every page (full table scan). With the index, you turn to the back, find "circuit breaker → pages 47, 93, 201," and jump directly there. The cost: maintaining the back-index means every time you add a page to the book, you also update the back-index. A book with 20 index entries is harder to update than a book with none. But finding things is dramatically faster.

---

### 💬 Interview Questions - Indexes

**"An order lookup by customer_id is slow. What do you do?"**
Check with EXPLAIN ANALYZE whether an index exists and whether it's being used. If no index on customer_id, add one. If low selectivity is causing the database to ignore the index, consider a composite index. Check if the query is actually hitting the right table or joining unnecessarily.

**"What's a covering index?"**
An index that includes all columns a query needs, so the database never has to visit the actual table rows. Example: `CREATE INDEX ON orders(customer_id) INCLUDE (status, total)` - a query selecting status and total for a customer can be served entirely from the index without a "heap fetch."

**"When would you NOT add an index to a column that's frequently queried?"**
Low selectivity (boolean, status with few values returning many rows). Very high write rate where write amplification outweighs read gains. Small tables where a full scan is already fast. Columns used in very infrequent queries that don't justify the ongoing maintenance cost.

## ⚡ Part 5: Transaction Isolation - What Happens When Two Users Touch the Same Data

### The Setup: Concurrent Order Updates

Two customer service representatives at Amazon are simultaneously looking at order #5678. Rep A is going to apply a $50 discount. Rep B is going to change the shipping address. They both read the order, make their change, and save.

This sounds simple. The reality involves several possible disasters depending on your isolation level.

We covered isolation levels conceptually earlier. Now let's see them through the lens of actual SQL and real scenarios.

---

### 🎭 The Anomalies, Illustrated

**Dirty Read - Reading Uncommitted Data:**

```
Timeline:                Rep A                    Rep B
                         
t=1                      BEGIN
t=2                      UPDATE orders SET total = 899.99 WHERE id = 5678
                         (not committed yet)
t=3                                               BEGIN
t=4                                               SELECT total FROM orders WHERE id = 5678
                                                  → sees 899.99 (DIRTY READ!)
t=5                      ROLLBACK  ← decides not to apply discount
t=6                                               Uses 899.99 in further calculations
                                                  → Based on data that never officially existed 💥
```

**Non-Repeatable Read - Same Query, Different Result:**

```
Timeline:                Rep A                    Fraud System

t=1                                               BEGIN
t=2                                               SELECT total FROM orders WHERE id = 5678
                                                  → 999.99
t=3                      BEGIN
t=4                      UPDATE orders SET total = 50.00 WHERE id = 5678
t=5                      COMMIT
t=6                                               SELECT total FROM orders WHERE id = 5678
                                                  → 50.00  ← DIFFERENT FROM t=2!
t=7                                               "Did total change? Flag for review."
                                                  → False positive fraud alert 💥
```

**Phantom Read - Same Query, Different Rows:**

```
Timeline:              Reporting Job             Order Service

t=1                    BEGIN
t=2                    SELECT COUNT(*) FROM orders WHERE customer_id = 123
                       → 5 orders
t=3                                              INSERT INTO orders (customer_id=123, ...)
                                                 COMMIT
t=4                    SELECT COUNT(*) FROM orders WHERE customer_id = 123
                       → 6 orders  ← New row appeared! PHANTOM!
t=5                    "Customer placed order during reporting window"
                       Report shows inconsistent numbers within one transaction 💥
```

---

### 🔒 Isolation Levels in PostgreSQL: The Practical Reality

```sql
-- Set isolation level for a transaction:
BEGIN TRANSACTION ISOLATION LEVEL READ COMMITTED;
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;

-- In Spring:
@Transactional(isolation = Isolation.READ_COMMITTED)
@Transactional(isolation = Isolation.REPEATABLE_READ)
@Transactional(isolation = Isolation.SERIALIZABLE)
```

| Isolation Level | Dirty Read | Non-Rep. Read | Phantom | Performance | Use When |
|---|---|---|---|---|---|
| READ UNCOMMITTED | Possible | Possible | Possible | Highest | Almost never - too dangerous |
| READ COMMITTED | Safe | Possible | Possible | High | Default; most OLTP workloads |
| REPEATABLE READ | Safe | Safe | Safe* | Medium | Financial reads, reports |
| SERIALIZABLE | Safe | Safe | Safe | Lowest | Strict correctness required |

*PostgreSQL's REPEATABLE READ also prevents phantoms (better than SQL standard requires)

**The practical advice:**

```
READ COMMITTED (default):
→ Good for: most application reads, writes that don't depend on
  the previous state of another row, high-throughput OLTP
→ Risk: non-repeatable reads in long transactions

REPEATABLE READ:
→ Good for: bank balance reads, inventory checks before deduction,
  any "read then conditionally write" logic
→ In PostgreSQL: also prevents phantoms

SERIALIZABLE:
→ Good for: complex business invariants that span multiple rows
  e.g., "total allocated inventory cannot exceed warehouse capacity"
→ Cost: PostgreSQL uses predicate locking - detects conflicts and
  aborts transactions. Application must handle serialization failures
  and retry.
```

---

### 🧩 Isolation and Indexes: How They Work Together

Isolation levels interact with indexes in a subtle way. When PostgreSQL implements REPEATABLE READ, it uses **Multi-Version Concurrency Control (MVCC)**:

```
MVCC: instead of locking rows for readers,
PostgreSQL keeps multiple versions of a row.

Row history for orders #5678:

Version 1 (xmin=100, xmax=200): total=999.99  ← visible to transactions started before xid=200
Version 2 (xmin=200, xmax=null): total=899.99 ← visible to transactions started after xid=200

Rep A's transaction (started at xid=150):
  Sees Version 1 → total=999.99
  
Rep B's transaction (started at xid=250):
  Sees Version 2 → total=899.99
  
No locking needed for reads!
Writers don't block readers. Readers don't block writers.
This is how PostgreSQL achieves high concurrency.
```

The consequence: **reads in PostgreSQL are never blocked by writes** (at READ COMMITTED and REPEATABLE READ). This is why PostgreSQL handles high concurrency so well.

## 🔮 Part 6: Optimistic Locking - High-Throughput Concurrent Updates

### The Problem Optimistic Locking Solves

Two product managers at Amazon are both editing the same product listing simultaneously. PM1 is updating the description. PM2 is updating the price. Without any concurrency control:

```
t=1   PM1 reads product #789: { name:"Laptop", price:999, description:"Old desc", version:5 }
t=2   PM2 reads product #789: { name:"Laptop", price:999, description:"Old desc", version:5 }
t=3   PM1 changes description to "New desc"
t=4   PM2 changes price to 899
t=5   PM1 saves: UPDATE products SET description="New desc" WHERE id=789
      → Succeeds. Product: { price:999, description:"New desc", version:5 }
t=6   PM2 saves: UPDATE products SET price=899 WHERE id=789
      → Succeeds. Product: { price:899, description:"Old desc", version:5 }
      ← PM1's description change is LOST. Last write wins. 💥
```

This is the **Lost Update** problem. PM2 saved a stale version of the row, overwriting PM1's change.

---

### 🔢 The Version Column: Detecting Stale Updates

Optimistic locking adds a `version` column. Every update increments the version. Before saving, check that the version you're saving matches what's in the database.

```sql
-- Table with version column:
CREATE TABLE products (
    id          BIGSERIAL PRIMARY KEY,
    name        VARCHAR(255) NOT NULL,
    price       DECIMAL(10,2) NOT NULL,
    description TEXT,
    version     INTEGER NOT NULL DEFAULT 0  ← the key
);

-- The "optimistic" UPDATE:
UPDATE products 
SET price = 899,
    description = 'Old desc',  ← PM2's version of description (stale)
    version = version + 1       ← increment version
WHERE id = 789
  AND version = 5;              ← only update if version matches what I read

-- Check rows affected:
-- If 1 row updated: success (nobody else updated between my read and write)
-- If 0 rows updated: conflict (someone else updated first - version is now 6)
```

Let's replay the scenario with optimistic locking:

```
t=1   PM1 reads: { price:999, description:"Old desc", version:5 }
t=2   PM2 reads: { price:999, description:"Old desc", version:5 }
t=3   PM1 updates: WHERE version=5 → sets description="New desc", version=6
      → 1 row affected ✅. DB now: { price:999, description:"New desc", version:6 }
t=4   PM2 updates: WHERE version=5 → sets price=899, version=6
      → 0 rows affected! ❌ version in DB is now 6, not 5.
      
PM2's application:
  "0 rows affected - someone else modified this record."
  Throw OptimisticLockException.
  Show PM2: "This product was updated by another user. Please refresh and retry."
  PM2 refreshes, sees current state { price:999, description:"New desc", version:6 }
  PM2 updates price to 899, version becomes 7.
  Both changes preserved. ✅
```

---

### ⚙️ Optimistic Locking in JPA/Hibernate

```java
@Entity
@Table(name = "products")
public class Product {
    
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    
    private String name;
    private BigDecimal price;
    private String description;
    
    @Version          // ← Hibernate manages this automatically
    private Integer version;
    
    // getters, setters
}
```

With `@Version`, Hibernate automatically:
- Adds `AND version = ?` to every UPDATE statement
- Increments the version on every save
- Throws `OptimisticLockException` if version mismatch (0 rows affected)
- You catch the exception and decide what to do (retry, inform user, merge)

**Handling the exception:**

```java
@Service
public class ProductService {
    
    @Retryable(
        value = OptimisticLockingFailureException.class,
        maxAttempts = 3,
        backoff = @Backoff(delay = 100)
    )
    @Transactional
    public void updatePrice(Long productId, BigDecimal newPrice) {
        Product product = productRepo.findById(productId)
            .orElseThrow();
        product.setPrice(newPrice);
        productRepo.save(product);
        // If OptimisticLockException: Spring retries up to 3 times
        // Each retry re-reads fresh data and re-applies the update
    }
}
```

### ⚔️ Optimistic vs Pessimistic: The Full Comparison

```
PESSIMISTIC LOCKING:
  SELECT * FROM products WHERE id = 789 FOR UPDATE;
  ← Row is LOCKED. Nobody else can update it until your transaction commits.
  
  PM1 acquires lock.
  PM2 tries to acquire lock: BLOCKED (waits).
  PM1 commits: lock released.
  PM2 unblocks: reads fresh data, makes update.
  
  ✅ No lost updates
  ✅ No retry logic needed
  ❌ Reduced concurrency (others wait)
  ❌ Risk of deadlock (if two transactions lock in different order)
  ❌ Long locks in slow transactions can block many others
  
OPTIMISTIC LOCKING:
  Read row (no lock).
  Process in application (potentially long time).
  Write with version check.
  If conflict: retry.
  
  ✅ No database locks held during processing
  ✅ Higher concurrency (no waiting for locks)
  ✅ No deadlock risk
  ❌ Retry logic required
  ❌ Higher contention → more retries → potential starvation under heavy load
  ❌ Not suitable for "increment by 1" operations (see below)
```

**When optimistic locking fails: the inventory decrement problem**

```
WRONG use of optimistic locking for inventory:

100 users simultaneously trying to buy the last item (stock=1):

User 1 reads: { stock:1, version:10 }
User 2 reads: { stock:1, version:10 }
...
User 100 reads: { stock:1, version:10 }

User 1 updates: SET stock=0, version=11 WHERE version=10 → SUCCESS
Users 2-100 update: WHERE version=10 → 0 rows affected → OptimisticLockException
Users 2-100 retry: read { stock:0, version:11 }
                   "stock is 0, can't proceed" → return out of stock ✅

Result: exactly one sale. ✅ Optimistic locking worked here.

BUT: with 10,000 concurrent users, 9,999 get exceptions and retry.
Each retry involves re-reading and re-trying.
Under extreme contention: retry storms.

BETTER for high-contention counters:
UPDATE inventory SET stock = stock - 1 WHERE product_id = ? AND stock > 0;
-- Atomic. No version check. Database handles concurrent decrements correctly.
-- Check rows_affected: 0 means out of stock, 1 means success.
-- This is a "conditional update" - no read-modify-write cycle needed.
```

### 🔗 Connecting Isolation + Indexes + Optimistic Locking

These three concepts reinforce each other in a real system:

```
Scenario: Inventory check before purchase

Step 1: Read inventory (isolation matters)
  @Transactional(isolation = REPEATABLE_READ)
  
  We read inventory: stock=5
  We need to ensure this read is stable during our transaction.
  REPEATABLE READ: the stock=5 read won't change within our transaction
  even if another transaction commits a change between our read and write.

Step 2: Index makes the read fast
  SELECT stock FROM inventory WHERE product_id = 789;
  
  Without index on product_id: full scan of inventory table.
  With index: direct lookup in O(log N).

Step 3: Optimistic locking prevents lost updates
  UPDATE inventory 
  SET stock = stock - 1, version = version + 1
  WHERE product_id = 789 AND stock > 0 AND version = 5;
  
  If version changed: someone else decremented first.
  Re-read: stock might now be 4 or 0.
  If 0: return out of stock.
  If > 0: retry decrement.

Step 4: Transaction commits
  All changes durable (ACID durability).
  Index updated to reflect new state.
  Version incremented.
```

### 🧠 Mental Model: Optimistic vs Pessimistic Locking

> **Pessimistic locking is like a library where you must physically check out a book before reading it.** While you have it, nobody else can borrow it. You're protected from others changing the book. But if you hold it for hours, everyone else is waiting.
>
> **Optimistic locking is like Google Docs offline mode.** You work on your local copy freely, with no locks. When you sync, if someone else changed the same section, you get a conflict notification. Usually conflicts are rare, so most of the time you sync successfully. Occasionally you need to resolve a conflict - but the benefit is that nobody was blocked while you were working.

### 💬 Interview Questions - Isolation + Optimistic Locking

**"What is the difference between optimistic and pessimistic locking and when would you use each?"**
Pessimistic: lock the row before reading; use when conflicts are frequent, operations are short, or you can't afford any retries (e.g., financial debit operations). Optimistic: version check at write time, retry on conflict; use when conflicts are rare, operations are long, or you need high concurrency (e.g., product catalog updates, user profile edits).

**"How would you handle a scenario where 10,000 users try to buy the last concert ticket simultaneously?"**
Optimistic locking would cause 9,999 retries - too much contention. Better: pessimistic lock on the ticket row (`SELECT FOR UPDATE`), or atomic conditional update (`UPDATE tickets SET owner=? WHERE id=? AND owner IS NULL`) checking rows_affected. For extreme scale: distributed lock via Redis with TTL.

**"What transaction isolation level would you use for a bank balance transfer?"**
REPEATABLE READ minimum, to ensure the balance you read at the start of the transaction remains stable. For strict "no other transaction can even read this balance during transfer," SERIALIZABLE. Combined with a pessimistic lock (`SELECT FOR UPDATE` on both accounts) to prevent two simultaneous transfers affecting the same accounts.

## 📊 Quick Reference: Key Decisions and Trade-offs

| Decision | Option A | Option B | Choose A when | Choose B when |
|---|---|---|---|---|
| Schema evolution | Flyway migrations | Hibernate ddl-auto | Production, teams, audit trail | Local dev only |
| Service databases | Database-per-service | Shared database | Microservices, scale | Monolith, small team |
| Concurrency control | Optimistic locking | Pessimistic locking | Low contention, long ops | High contention, short ops |
| Index strategy | Selective indexes | Index everything | High write rate, large tables | Read-heavy, small tables |
| Isolation level | READ COMMITTED | REPEATABLE READ | High throughput OLTP | Financial, reporting |
| Cross-service query | API composition | Shared read model | Occasional queries | Frequent complex queries |

---

### ⚠️ Common Mistakes

❌ **Using `ddl-auto=update` in production.** Schema changes happen silently, irreversibly, without review or audit trail. Always use `validate` in production and Flyway for migrations.

❌ **Indexing every column "just in case."** Every index slows writes. Index the columns your actual query patterns use, verified with EXPLAIN ANALYZE.

❌ **Optimistic locking on high-contention counters.** Using `@Version` on an inventory counter that 10,000 users hit simultaneously causes retry storms. Use atomic SQL updates instead.

❌ **Sharing a database between microservices.** Creates schema coupling, scaling coupling, and technology coupling. Defeats the purpose of the microservices split.

❌ **Non-nullable columns in migrations without defaults.** `ALTER TABLE orders ADD COLUMN promo_code VARCHAR(50) NOT NULL` fails on a non-empty table. Always add as nullable, backfill, then constrain.

❌ **Using SERIALIZABLE isolation everywhere.** It provides the strongest guarantees but aborts transactions on conflicts and requires retry logic. Use it only where the business rule genuinely requires it.

❌ **Forgetting to index FK columns.** Every foreign key should typically have an index. When you `JOIN orders ON orders.customer_id = customers.id`, an unindexed `customer_id` causes a full scan of the orders table.
