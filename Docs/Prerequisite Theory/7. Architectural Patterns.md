# 🏛️ Architectural Patterns in HLD

*The recurring solutions to recurring problems in large-scale system design.*

---

## 🗺️ The Patterns We'll Cover

```
CQRS         → separate reads from writes
Event Sourcing → store events, not state
Saga          → already covered (distributed transactions)
Strangler Fig → migrate monoliths safely
Sidecar       → infrastructure without changing app code
Service Mesh  → sidecar at scale
Backends for Frontends (BFF) → tailor APIs per client
```

Each pattern exists because a specific force - scale, team structure, data shape, deployment complexity - made the simpler approach painful. We'll find the pain first.

---

## 🔀 Pattern 1: CQRS - Command Query Responsibility Segregation

### The Problem: One Model Can't Serve Two Masters

In a standard application, you have one data model that handles both writes and reads.

Amazon's Order Service: you write an order (complex validation, business rules, multiple tables) and you also read orders (complex joins - customer details, item names, shipment status, payment info, all in one response).

```
TRADITIONAL (one model, one database):

Write: POST /orders
  → Validate inventory, apply discount rules, calculate tax,
    create order, create order_items, update inventory,
    trigger payment - COMPLEX WRITE LOGIC

Read: GET /orders?userId=123&status=SHIPPED&sort=recent
  → JOIN orders, order_items, products, customers,
    shipments, payments - COMPLEX READ LOGIC
    
One model trying to be optimal for both.
Result: optimal for neither.
```

**The write model** wants normalized tables, ACID transactions, business rule enforcement, strict constraints.

**The read model** wants denormalized data, fast lookups, pre-joined data, flexible querying, often different shapes for different screens (mobile vs desktop vs analytics).

These are fundamentally conflicting requirements. CQRS says: **stop trying to satisfy both with one model.**

---

### ✂️ The Split: Commands vs Queries

**Command** = an intent to change state. Has business rules. Produces events. Returns minimal data (success/failure, maybe an ID).

**Query** = a request for data. Has no side effects. Can be stale. Returns rich, shaped data.

```
CQRS ARCHITECTURE:

         WRITE SIDE (Command Model)          READ SIDE (Query Model)
         
Client ──► Command Handler                  Client ──► Query Handler
              │                                            │
              │ validates, enforces                        │ reads from
              │ business rules                             │ optimized
              ▼                                            ▼
         Write DB                            Read DB (or multiple)
         (normalized,                        (denormalized,
          ACID,                               pre-joined,
          PostgreSQL)                         fast,
              │                               Elasticsearch/Redis/
              │ emits events                  read-replica)
              ▼                                            ▲
         Event Bus ────────────────────────────────────────┘
         (Kafka)              Projections
                         (event handlers that
                          update read models)
```

The write side persists to a normalized database and publishes events. **Projections** (also called read model updaters) consume those events and update denormalized read models optimized for specific queries.

---

### 🛍️ Real Example: Amazon Order History Page

```
WRITE SIDE: Place order
  OrderService.placeOrder(command):
    - Validates payment method
    - Checks inventory
    - Applies promotions
    - Creates Order + OrderItems (normalized, 3 tables)
    - Publishes OrderPlaced event

READ SIDE: Display order history page
  User sees: order thumbnail, product image, price paid,
             delivery status, estimated arrival, return eligibility
             
  Without CQRS: JOIN 7 tables, aggregate shipment events,
                calculate return window, format for display.
                Slow. Complex. Same query for every page load.
  
  With CQRS: OrderProjection listens to events and maintains:
  
  order_history_view table:
  {
    orderId: "A-98765",
    userId: "u-123",
    placedAt: "2024-01-15",
    totalFormatted: "$999.99",
    statusLabel: "Delivered Jan 17",
    productImageUrl: "https://cdn...",
    productName: "Sony Headphones",
    canReturn: true,
    returnDeadline: "2024-02-14"
  }
  
  GET /orders?userId=123 → SELECT * FROM order_history_view WHERE userId=123
  Single table, no joins, milliseconds. ✅
```

---

### ⚠️ The Consistency Trade-off: Eventual Reads

The read model is updated asynchronously via events. This means after you place an order, there is a brief window (milliseconds to seconds) where the order isn't in the read model yet.

```
t=0   User places order → write DB updated ✅
t=0   OrderPlaced event published to Kafka
t=1   User's page refreshes: GET /my-orders
t=1   Projection hasn't processed event yet
      → Order doesn't appear yet 😕
t=2   Projection processes event, updates read model
t=2   User refreshes again → order appears ✅
```

This is **eventual consistency on the read side.** For most use cases, a 1-2 second delay is acceptable. For some (stock trading, payment confirmation), it isn't - those cases need synchronous read-your-writes consistency and may not suit pure CQRS.

---

### 🎯 When to Use CQRS

**Use it when:**
- Read patterns and write patterns have fundamentally different shapes
- Read load vastly exceeds write load (scale reads independently)
- You need multiple read representations of the same data (mobile, web, analytics)
- Complex domain logic on the write side that shouldn't pollute read code
- You need full-text search (Elasticsearch) alongside transactional writes (PostgreSQL)

**Don't use it when:**
- Simple CRUD application - the complexity isn't justified
- Team is small and operational overhead of maintaining two models is too high
- Strong consistency on reads is required (can be worked around but adds complexity)
- The system is early stage - add CQRS when the pain of not having it is felt

---

### 🧠 Mental Model: CQRS

> **CQRS is like separating the kitchen from the dining room.** The kitchen (write side) is optimized for cooking - specialized stations, raw ingredients, strict hygiene rules, complex preparation. The dining room (read side) is optimized for eating - beautifully plated, pre-arranged, fast service. Trying to eat raw ingredients in the kitchen or cook in the dining room works terribly. Separating them lets each be perfect at its job. The waiter (event/projection) carries dishes between them.

## 📜 Pattern 2: Event Sourcing - Store Events, Not State

### The Problem: State Is a Lie

In every traditional system, you store **current state**:

```
accounts table:
┌────────────┬─────────────┬──────────────┐
│ account_id │ balance     │ updated_at   │
├────────────┼─────────────┼──────────────┤
│ ACC-001    │ $1,247.50   │ 2024-01-15   │
└────────────┴─────────────┴──────────────┘
```

Balance is $1,247.50. But:

- **How did it get there?** Unknown.
- **What was the balance on Jan 10th?** Unknown. The row was overwritten.
- **What sequence of deposits and withdrawals led here?** Unknown.
- **Was there a bug 3 days ago that incorrectly modified this balance?** Impossible to verify.
- **Can we rebuild the balance if the row gets corrupted?** No. It's gone.

Every update **destroys the previous state.** This is fine for most domains. For some - banking, auditing, legal, inventory - it's catastrophic.

---

### 📋 Event Sourcing: Append-Only Event Log as the Source of Truth

Instead of storing current state, **store every event that ever happened.** Current state is derived by replaying events.

```
account_events table (APPEND ONLY - never UPDATE or DELETE):

┌────────────┬─────────────────────┬──────────────┬────────────┬────────────┐
│ event_id   │ event_type          │ aggregate_id │ payload    │ timestamp  │
├────────────┼─────────────────────┼──────────────┼────────────┼────────────┤
│ evt-001    │ AccountOpened       │ ACC-001      │ {init:0}   │ Jan 1      │
│ evt-002    │ MoneyDeposited      │ ACC-001      │ {amt:500}  │ Jan 3      │
│ evt-003    │ MoneyDeposited      │ ACC-001      │ {amt:1000} │ Jan 7      │
│ evt-004    │ MoneyWithdrawn      │ ACC-001      │ {amt:200}  │ Jan 10     │
│ evt-005    │ MoneyDeposited      │ ACC-001      │ {amt:300}  │ Jan 12     │
│ evt-006    │ MoneyWithdrawn      │ ACC-001      │ {amt:352.50}│ Jan 15    │
└────────────┴─────────────────────┴──────────────┴────────────┴────────────┘

Current balance = replay all events:
  0 + 500 + 1000 - 200 + 300 - 352.50 = $1,247.50 ✅

Balance on Jan 10 = replay up to Jan 10:
  0 + 500 + 1000 - 200 = $1,300.00 ✅ (impossible with traditional state storage)
```

---

### 🔄 How Event Sourcing Works in Practice

```
WRITE PATH:

Command arrives: WithdrawMoney { accountId: ACC-001, amount: 352.50 }
    │
    ▼
Load aggregate: replay all ACC-001 events → reconstruct Account object
    │           (or load from snapshot + events since snapshot)
    ▼
Apply business rules:
    Account.withdraw(352.50)
      → check balance >= 352.50  ✅ ($1,600 > $352.50)
      → validate not frozen        ✅
      → apply withdrawal           
    │
    ▼
Produce event: MoneyWithdrawn { accountId: ACC-001, amount: 352.50, balanceAfter: 1247.50 }
    │
    ▼
Append to event store (single INSERT, never UPDATE)
    │
    ▼
Publish event to Kafka → projections update read models


READ PATH:

GET /accounts/ACC-001/balance
  → Query pre-built read model (balance_view table, updated by projection)
  → Return $1,247.50 (no event replay needed for reads)

GET /accounts/ACC-001/transactions?from=Jan1&to=Jan10
  → Query transaction_history_view (projection-built from events)
  → Return list of transactions
```

---

### 📸 Snapshots: Solving the Replay Performance Problem

Replaying thousands of events on every write becomes slow for long-lived aggregates.

```
Without snapshots:
  Account ACC-001 has 50,000 events over 5 years.
  Every withdrawal: load and replay 50,000 events → slow! 😩

With snapshots:
  Every 100 events (or daily): save a snapshot of current state.
  
  snapshot table:
  { accountId: ACC-001, balance: 1247.50, version: 49,982, at: Jan 15 }
  
  On load: fetch latest snapshot + only events AFTER snapshot version
  → Load snapshot (1 row) + 18 recent events = fast! ✅
```

---

### 🎬 Real World: Netflix and Event Sourcing

Netflix uses event sourcing for their billing system. Every subscription change, plan upgrade, payment, refund, and credit is stored as an immutable event. This gives them:

- **Full audit trail:** "Why is this customer's bill $15.99?" → replay events → trace every change
- **Temporal queries:** "What was this customer's plan on March 3rd?" → replay to that date
- **Bug recovery:** "Billing calculation was wrong for 3 days" → fix the calculation, replay events, recompute all affected bills
- **Regulatory compliance:** Financial regulations require complete transaction history. Event sourcing provides it naturally.

---

### ⚔️ CQRS + Event Sourcing: The Natural Pair

CQRS and Event Sourcing are independent patterns but combine naturally:

```
Event Sourcing → produces events naturally (they're the source of truth)
CQRS → reads are projections built from those events

Together:

WRITE: Command → Event Sourced Aggregate → Append event to store
                                                    │
                                            Publish to Kafka
                                                    │
READ:                                    Projection builds
                                         read model from events
                                                    │
                                         Query Handler reads
                                         from read model
```

This is the architecture used in financial systems, audit-heavy domains, and anywhere temporal querying matters.

---

### ✅❌ Event Sourcing Trade-offs

| Benefit | Cost |
|---|---|
| Complete audit trail | Complexity - steep learning curve |
| Temporal queries (state at any point in time) | Event schema evolution is hard |
| Bug recovery via replay | Replay time (mitigated by snapshots) |
| Natural event-driven integration | Eventual consistency on reads |
| No UPDATE/DELETE bugs | Querying current state requires projections |
| Debugging is powerful | Team must understand the pattern deeply |

**Don't use Event Sourcing for:** Simple CRUD (overkill), small teams without experience, domains where history genuinely doesn't matter.

**Do use it for:** Financial transactions, inventory movements, audit-required domains, anywhere "how did we get here?" is a business question.

---

### 🧠 Mental Model: Event Sourcing

> **Event Sourcing is accounting.** Accountants don't store your "current balance" and overwrite it with each transaction. They record every transaction in a ledger - every debit, every credit, in order, immutably. Your current balance is derived by summing the ledger. This gives you auditing, historical queries, and the ability to find and correct errors. Traditional state storage is like a bank that just updates a single number on a whiteboard and erases the old one. Event Sourcing keeps the full ledger.

## 🪴 Pattern 3: Strangler Fig - Migrating Monoliths Without Big Bang Rewrites

### The Problem: You Can't Stop the World to Rewrite It

You have a 10-year-old monolith. 2 million lines of code. 500,000 daily active users. Your team wants to move to microservices. The naive approach: "Let's rewrite the whole thing from scratch."

This is known as **the second-system effect** or the **big bang rewrite**, and it almost always fails:

```
BIG BANG REWRITE PROBLEMS:

Year 1: New system being built. Old system still running.
        Team split: some maintain old, some build new.
        Old system keeps getting new features (business doesn't pause).
        New system is always "almost done."

Year 2: New system is feature-complete... for Year 1's requirements.
        Old system has 1 year of new features new system doesn't have.
        Customers can't migrate: missing features they rely on.

Year 3: New system deployed. Bugs everywhere that old system didn't have.
        Edge cases only discovered after real traffic hits it.
        Rollback? Can't - 2 years of work thrown away.
        
Historical examples of failed big bang rewrites:
  Netscape 6 (took 3 years, product died)
  HealthCare.gov (rewrite after initial failure, years of work)
  Many enterprise SAP/Oracle migrations
```

The Strangler Fig pattern offers a safer alternative: **incrementally replace the monolith, piece by piece, while it's running in production.**

---

### 🌿 The Strangler Fig: How the Tree Works

Named after the strangler fig tree in nature: the fig vine wraps around a host tree, slowly grows, eventually replaces it. The host tree doesn't know it's being replaced.

```
PHASE 1: Introduce a facade (proxy/router) in front of monolith

     All traffic
         │
         ▼
    ┌─────────────┐
    │    Proxy    │   ← new component, routes all traffic
    └──────┬──────┘
           │ 100% of traffic
           ▼
    ┌─────────────┐
    │   Monolith  │   ← unchanged, still handles everything
    └─────────────┘

PHASE 2: Extract first service (e.g., Payments)

     All traffic
         │
         ▼
    ┌─────────────┐
    │    Proxy    │   ← now routes based on path/feature
    └──────┬──────┘
           │                    │
           │ /payments/*        │ everything else
           ▼                    ▼
    ┌─────────────┐      ┌─────────────┐
    │  Payment    │      │   Monolith  │
    │  Service    │      │  (smaller)  │
    └─────────────┘      └─────────────┘

PHASE 3, 4, 5... Extract more services

     All traffic
         │
         ▼
    ┌─────────────┐
    │    Proxy    │
    └──────┬──────┘
     │     │     │
     ▼     ▼     ▼
  Payment  Order  Inventory
  Service  Service Service
                       │
               ┌───────┘
               ▼
           Monolith
           (tiny remnant,
            eventually gone)

PHASE FINAL: Monolith is dead. Proxy routes to all microservices.
```

---

### 🔧 The Proxy Layer: How Routing Works

The proxy (often an API Gateway or a simple reverse proxy like Nginx/Envoy) decides where to send each request:

```
Route /api/payments/*  → Payment Service (new)
Route /api/orders/*    → Order Service (new)
Route /api/inventory/* → Inventory Service (new)
Route /api/*           → Monolith (everything not yet extracted)
```

Users see no change. The same URLs, same behavior. The proxy is invisible. The monolith shrinks over time as routes migrate away from it.

---

### 🗃️ The Hard Part: Data Migration

Moving functionality is relatively straightforward. Moving data is hard.

```
STRATEGY: Synchronize data during transition period

Step 1: New Payment Service is deployed
Step 2: Payment Service has its own DB (empty)
Step 3: Dual-write period:
          Monolith writes to its DB AND calls Payment Service
          Payment Service writes to its own DB
          Payment Service reads from its DB
          Monolith DB = source of truth during this phase
          
Step 4: Backfill historical data from monolith DB to Payment Service DB

Step 5: Verify data consistency between the two DBs

Step 6: Cut over - Payment Service DB is now source of truth
        Monolith no longer owns payment data
        Remove dual-write code from monolith
```

This requires significant discipline and is the reason strangler migrations take months to years - the code move is fast, the data migration and verification is slow.

---

### 📋 Strangler Fig in Practice: Uber's Migration

Uber famously migrated from a monolithic Node.js application ("Uber Monolith") to microservices using a strangler fig approach:

```
Original: One Node.js app handling everything
          (driver tracking, dispatch, payments, users, maps)

Migration order (by business impact and team ownership):
  1. Trip Service extracted (core, high value)
  2. Driver Location Service extracted (high write rate, needed separate scaling)
  3. Payment Service extracted (compliance, PCI isolation)
  4. Notification Service extracted (easy, low risk)
  5. ... continued over several years

Proxy: API Gateway routing by URI prefix and domain
Data: Each service got its own database, data migrated in phases

Result: Uber now has ~2,000+ microservices.
The monolith is gone.
Migration took ~3-4 years with continuous production traffic.
```

---

### 🧠 Mental Model: Strangler Fig

> **The Strangler Fig is like renovating a house while living in it.** You don't knock the whole house down and live in a hotel for 2 years while it's rebuilt (big bang rewrite). You renovate one room at a time. First the kitchen. Then the bathroom. Then the bedroom. You still live there throughout. Each room is better than before. Eventually, the old house is completely replaced - but you never lost your home. The "proxy" is the front door that still works no matter what room is being renovated.

## 🔧 Pattern 4: Sidecar - Infrastructure Without Changing Application Code

### The Problem: Cross-Cutting Concerns Spread Everywhere

In a microservices system, every service needs:
- TLS termination and mTLS between services
- Retry logic and circuit breakers
- Distributed tracing instrumentation
- Metrics collection
- Rate limiting
- Access logging
- Service discovery

The naive approach: each service implements all of this. In Java Spring Boot, you add Spring Cloud libraries. In Python services, you add equivalent Python libraries. In Go services, you add Go equivalents.

```
PROBLEMS WITH LIBRARY APPROACH:

- 20 services × 5 cross-cutting concerns = 100 implementations
- Library updates require redeploying ALL services
- Language-specific: Java library doesn't help Python service
- Teams spend time on infrastructure, not business logic
- Inconsistent implementations across services
- Testing infrastructure code in every service
```

The Sidecar pattern says: **run a second container alongside every service container that handles all infrastructure concerns transparently.**

---

### 🏍️ The Sidecar: Second Container, Same Pod

In Kubernetes, a Pod can run multiple containers. The sidecar is a second container that shares the same network namespace as the main application container.

```
KUBERNETES POD:

┌─────────────────────────────────────────────┐
│                    POD                       │
│                                             │
│  ┌──────────────────┐  ┌──────────────────┐ │
│  │  Order Service   │  │  Sidecar Proxy   │ │
│  │  (your code)     │  │  (Envoy)         │ │
│  │                  │  │                  │ │
│  │  Port 8080       │  │  Port 15001      │ │
│  │  (app traffic)   │  │  (intercepts all │ │
│  │                  │  │   in/out traffic)│ │
│  └──────────────────┘  └──────────────────┘ │
│                                             │
│  Shared network namespace                   │
│  (same localhost, same IP)                  │
└─────────────────────────────────────────────┘
```

All **inbound and outbound traffic** to/from the Order Service is transparently intercepted by the sidecar. The Order Service code is completely unaware of the sidecar's existence.

---

### 🛡️ What the Sidecar Handles

```
INBOUND TRAFFIC (from other services to Order Service):
  ✅ mTLS termination (verifies caller's certificate)
  ✅ Authentication check (is this caller authorized?)
  ✅ Rate limiting (too many requests? reject with 429)
  ✅ Tracing span creation (receive traceparent, create span)
  ✅ Access logging (structured log of every request)
  → Forwards to Order Service on localhost:8080

OUTBOUND TRAFFIC (from Order Service to other services):
  ✅ mTLS origination (attaches this service's certificate)
  ✅ Retry logic (retry on 5xx with backoff)
  ✅ Circuit breaking (fail fast if downstream is down)
  ✅ Load balancing (distribute across downstream instances)
  ✅ Tracing propagation (add traceparent to outbound requests)
  → Routes to destination service
```

Order Service code simply calls `http://inventory-service/reserve` on localhost. The sidecar handles service discovery, load balancing, mTLS, retries, and tracing automatically.

---

### ⚙️ Service Mesh: Sidecars at Scale

When every service in your system has a sidecar, you have a **Service Mesh.** The mesh has two layers:

```
DATA PLANE: All the sidecar proxies (Envoy instances)
            Handle actual traffic between services
            
CONTROL PLANE: Central configuration manager (Istio, Linkerd)
               Tells all sidecar proxies:
               - What TLS certificates to use
               - What retry policies to apply
               - What circuit breaker thresholds to set
               - What to log and what to trace
               - Which services can talk to which (authorization)
               
ARCHITECTURE:

Control Plane (Istio)
    │
    │ pushes config to
    ▼
┌────────┐  ┌────────┐  ┌────────┐  ┌────────┐
│Sidecar │  │Sidecar │  │Sidecar │  │Sidecar │
│(Envoy) │  │(Envoy) │  │(Envoy) │  │(Envoy) │
├────────┤  ├────────┤  ├────────┤  ├────────┤
│ Order  │  │Payment │  │Inventory│ │Shipping│
│Service │  │Service │  │Service │  │Service │
└────────┘  └────────┘  └────────┘  └────────┘
```

**Real-world users:** Netflix, Lyft (created Envoy), Google (created Istio), Uber, Airbnb.

---

### ⚠️ Sidecar/Service Mesh Trade-offs

| Benefit | Cost |
|---|---|
| Language-agnostic infrastructure | Added latency (extra network hop) |
| Centrally managed policies | Complexity - new failure modes |
| Zero application code changes | Resource overhead (every pod runs 2 containers) |
| Consistent behavior across all services | Debugging is harder (traffic goes through proxy) |
| mTLS between all services automatically | Team must learn new operational tooling |

**Use when:** Large organization, polyglot services (multiple languages), strong security requirements (mTLS everywhere), need for unified observability across all services.

**Skip when:** Small team, homogeneous technology stack, simpler network requirements.

---

### 🧠 Mental Model: Sidecar

> **The Sidecar is like having a personal assistant attached to every employee.** The employee (your service) focuses entirely on their work (business logic). The assistant (sidecar) handles all administrative tasks: scheduling, communication protocols, security badges, meeting notes (tracing), expense reports (metrics). The employee doesn't know or care how the assistant does it. Hire a new employee (deploy a new service)? They automatically get an assistant. Change the communication policy company-wide? Update the assistant's training (control plane), not each employee.

## 📱 Pattern 5: Backends for Frontends (BFF)

### The Problem: One API, Many Clients, Nobody Happy

Your API was designed for the web browser. Now you have a mobile app, a smart TV app, a third-party partner API, and a voice assistant. They all hit the same backend.

```
PROBLEMS WITH ONE GENERIC API:

Mobile app:
  Needs smaller payloads (bandwidth constrained)
  Needs different data shapes (smaller screens)
  Makes 7 API calls to compose one screen → slow on mobile networks
  
Smart TV:
  Needs high-resolution image URLs
  Needs different navigation data
  Doesn't need purchase functionality
  
Third-party partners:
  Need bulk data access
  Need different authentication (API keys, not sessions)
  Need rate-limited, versioned, stable APIs
  
Voice assistant:
  Needs text-only responses
  Needs simplified product descriptions
  Doesn't need image URLs at all

One generic API serves all clients poorly.
```

The BFF pattern creates **a dedicated backend for each frontend type.** Each BFF is owned by the frontend team and optimized for their client's specific needs.

---

### 🏗️ BFF Architecture

```
                    Clients
     ┌──────────────┼──────────────┬──────────────┐
     ▼              ▼              ▼              ▼
 Mobile App      Web Browser    Smart TV    Partner API
     │              │              │              │
     ▼              ▼              ▼              ▼
┌─────────┐   ┌─────────┐   ┌─────────┐   ┌─────────┐
│ Mobile  │   │  Web    │   │  TV     │   │ Partner │
│  BFF    │   │  BFF    │   │  BFF    │   │  BFF    │
└────┬────┘   └────┬────┘   └────┬────┘   └────┬────┘
     │              │              │              │
     └──────────────┼──────────────┘              │
                    │                             │
            ┌───────┼───────────────┐             │
            ▼       ▼               ▼             ▼
         Order   Product        User          Inventory
         Service  Service       Service        Service
```

Each BFF:
- **Aggregates** multiple downstream service calls into one response
- **Transforms** data into the shape the client needs
- **Handles** client-specific auth and session management
- **Optimizes** payload size, field selection, caching for its client
- **Owned** by the team building the frontend (not a separate API team)

---

### 📦 BFF in Action: Product Page on Amazon

```
Web BFF: GET /web/products/789

Web BFF calls (in parallel):
  → Product Service: GET /products/789 (full details, HD images)
  → Inventory Service: GET /inventory/789 (stock count)
  → Reviews Service: GET /reviews?productId=789&page=1&size=10
  → Recommendations Service: GET /recommendations?productId=789

Aggregates into one response optimized for web:
{
  "product": { full details, large images, all specifications },
  "inventory": { stockCount: 47, inStock: true },
  "reviews": { items: [...10 reviews...], totalCount: 1847, avgRating: 4.3 },
  "recommendations": { items: [...12 products...] }
}

Mobile BFF: GET /mobile/products/789

Mobile BFF calls (with different parameters):
  → Product Service: GET /products/789?fields=name,price,thumbnailUrl
  → Inventory Service: GET /inventory/789 (just inStock boolean)
  → Reviews Service: GET /reviews?productId=789&page=1&size=3 (fewer reviews)
  → Recommendations Service: GET /recommendations?productId=789&size=4

Aggregates into compressed mobile response:
{
  "name": "Sony Headphones",
  "price": "$299",
  "thumbnail": "https://cdn/.../thumb_789.jpg",
  "inStock": true,
  "topReviews": [ 3 reviews only ],
  "recommendations": [ 4 products only ]
}
```

Mobile app makes **one HTTP call** instead of four. Gets exactly what it needs. No more, no less.

---

### 🧠 Mental Model: BFF

> **BFF is like having a personal shopper for each type of customer.** A personal shopper for a teenager needs different things than one for a 60-year-old executive. Rather than one generic shopper serving everyone adequately, each customer type gets a specialist who knows exactly what they need, speaks their language, and prepares exactly what they want. The actual stores (backend services) don't change - only the intermediary who translates between the customer and the stores is specialized.

## 📊 Pattern Decision Guide

| Pattern | Use When | Avoid When |
|---|---|---|
| CQRS | Reads and writes have different shapes/scale | Simple CRUD, small team |
| Event Sourcing | Audit trail required, temporal queries needed | Simple domains, no history needed |
| Strangler Fig | Migrating a live monolith incrementally | Greenfield (just build services directly) |
| Sidecar/Service Mesh | Polyglot services, strict mTLS, large org | Small homogeneous team |
| BFF | Multiple different client types | One client type, simple API needs |

## 💬 Common Interview Questions

**"How would you migrate Amazon's monolith to microservices without downtime?"**
Strangler Fig. Introduce API Gateway in front of monolith. Extract services one bounded context at a time, starting with least risky and highest business value. Dual-write during data migration. Route traffic progressively. Test each extraction in production with a small traffic percentage.

**"What is CQRS and why would you use it?"**
Separate write model (optimized for business rules, normalized) from read model (optimized for queries, denormalized). Use when read and write patterns diverge significantly, when you need multiple read representations, or when read load vastly exceeds write load. Trade-off: eventual consistency on reads.

**"What is the difference between CQRS and Event Sourcing?"**
They're independent. CQRS separates read and write models. Event Sourcing stores events as the source of truth instead of current state. They combine naturally - Event Sourcing produces events that CQRS projections consume to build read models - but you can use either without the other.

**"How does a Service Mesh improve security?"**
Automatic mutual TLS (mTLS) between all services without changing application code. Every service-to-service call is encrypted and both sides are authenticated via certificates. Authorization policies (Service A can call Service B but not Service C) are enforced at the mesh level. Certificates are rotated automatically.

**"How would you design an API for both mobile and web clients?"**
BFF pattern. Web BFF: richer data, multiple aggregated calls, larger payloads, desktop-optimized shapes. Mobile BFF: minimal fields, single aggregated call, compressed payload, mobile-optimized. Both BFFs call the same downstream services with different parameters. Each BFF owned by its client team.
